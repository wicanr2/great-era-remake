# RE-05 戰鬥狀態記錄：`MEM_WAR.DAT` 與 `SAVE(N).DT2` 的 469 B

> 輸入檔：`WAR.EXE`（375,568 B）
> SHA-256：`11dbfcf24686ab7765f788b38514cefd2039d0f60b6bd517d89fb5a84c068015`
> 位址是 IDA database 的 linear address
> 日期：2026-08-01

---

## 1. 讀寫兩邊都拆給你看

`sub_4F468` 讀檔、`sub_3964E` 寫檔，兩支用**同一組偏移**在記錄與全域變數
之間搬資料。Turbo Pascal 的 `$basg`（bitcopy）呼叫直接把每一段的大小
寫在參數裡，所以結構不用猜：

```
Assign(f, 'mem_war.dat')
Reset(f, 1D5h)                  ← recsize = 469
Seek(f, byte_6FFC4 - 1)         ← 省編號 - 1（與 nwmap.dat 同一個變數）
Read(f, buf)
```

`byte_6FFC4` 是「當前省編號」，`NWMAP.DAT`（`docs/spec/04`）用的也是它。

## 2. 469 B 的欄位切法

| 偏移 | 大小 | 搬去哪 | 觀察 |
|---:|---:|---|---|
| +0 | 4 × u16 | `word_64932/64936/6493A/6493E` | **第一方帶進場的黃金／糧食／彈藥／燃料**；第二方同名執行期欄位不在此記錄 |
| +8 | 10 B | `byte_6AA8C` | 10-byte 成對槽位；樣本以 `0xFF` 表示空槽，元素語意未知 |
| +18 | 10 B | `byte_6AA96` | 另一方的 10-byte 成對槽位；元素語意未知 |
| +28 | 10 × u16 | `word_64902` | **攻方的參戰單位**（將領 ID），空槽填 0 |
| +48 | 10 × u16 | `word_64916` | **守方的參戰單位** |
| +68 | **100 × u16** | `word_6A8F4` | 攻方的單位陣列，見 §2b |
| +268 | **100 × u16** | `word_6A9BC` | 守方 |
| +468 | 1 B | `byte_6AB65` | **攻方的來源省編號**，見下 |

```
8 + 10 + 10 + 20 + 20 + 200 + 200 + 1 = 469
```

**零剩餘**，而且寫檔函式用同一組偏移搬回去，兩邊對稱。

### `+0..+7` 是第一方帶的資源 — **confirmed**

`sub_546D1`（戰後結算）把這四個變數與**緊接其後的另外四個**兩兩相加，
寫回省份記錄的資源欄位：

```
省份.黃金 = min(word_64932 + word_64934, 60000)
省份.糧食 = min(word_64936 + word_64938, 60000)
省份.彈藥 = min(word_6493A + word_6493C, 60000)
省份.燃料 = min(word_6493E + word_64940, 60000)
```

所以**目標位址間隔 4 是因為每個欄位是一對**（兩方各一份）；但只有
`word_64932/36/3A/3E` 這一方被 `sub_4F468` 從 469-byte 記錄 +0..+7
讀出。`word_64934/38/3C/40` 在 `sub_3964E` 的同一分支直接寫入省份記錄，
不是第二份 DT2 header。記錄中的 A/B 暫時只表示這個搬運方向，不能從欄位名
推定所有分支的攻守角色。

煤礦與鐵礦不在其中——那是省份的礦藏，不隨部隊移動
（`docs/mechanics/40-economy.md` §5c）。

### 2a. `+8`／`+18` 的 10-byte 成對槽位 — **shape confirmed，元素語意 unknown**

`sub_4F468` 與 `sub_3964E` 分別以 `0Ah`（10）呼叫 `@$basg`，對稱搬運
`byte_6AA8C`／`byte_6AA96`。目前樣本有 `0xFF` 空槽與 0..190 的非空值，
可確認長度與哨兵分佈；但在已匯出的 IDA 直接讀／寫端，尚未找到能把單一 byte
接到部隊 ID、單位 ID 或旗標定義的完整資料流。因此：

- parser 只把兩區當作 raw-preserving 的 `[10]byte`；
- `OccupiedA/B` 只計算「不是 `0xFF`」，不把數值解釋成玩法資料；
- 未取得更多寫入端或正常戰鬥快照前，不得把它們命名為部署旗標或部隊編號。

### 2b. 戰鬥狀態有兩層：10 個部隊、100 個單位 — **confirmed**

三組都是成對的（攻守各一份），但**不是同一個層級**：

| 組 | 每方 | 層級 |
|---|---:|---|
| 10 B | 10 | 部隊 |
| 10 × u16 | 10 | 部隊（將領 ID，見上）|
| **200 B** | **100 × u16** | **單位** |

#### [訂正] 200 B 不是「10 個單位 × 20 B」

本節原本假設「若每方 10 個單位，200 ÷ 10 = 20 B/單位」。**那是錯的。**

`sub_545B0` 與 `sub_5446D` 遍歷 `word[0x6742 + i*2]` 與 `word[0x680A + i*2]`
時，**迴圈上限是 `64h = 100`**，而且是以 word 為單位（`shl di, 1`）。
兩個基址相差 `0xC8 = 200 bytes = 100 word`。

所以 200 B = **100 個 u16**，不是 10 筆 20 B 的記錄。

對照原版的詞表也說得通：`3.15` 的 48 是「**單位數**」、49 是「**士兵數**」
——本來就是兩個不同的量。

#### 執行期的四張清單

| 基址 | 每方格數 | 用在哪 |
|---|---:|---|
| `0x750` / `0x764` | 10 | `sub_543C2`、`sub_5446D`（部隊層的回合初始化）|
| `0x6742` / `0x680A` | 100 | `sub_545B0`、`sub_5446D`、`sub_54826`（單位層）|

`sub_5446D` 同時處理兩層——它的迴圈上限有 `0Ah` 也有 `64h`。

### 2c. `+68`／`+268` 對應 runtime 將領 ID 的元素定位 — **confirmed（IDA Pro 9.4）**

前一版只確認了兩區是 100×u16，沒有替每格指派語意。本輪以同一份
`WAR.EXE.i64` 重匯出建立端與讀取端，將資料流閉合到 runtime 將領記錄：

| 位址／函式 | 原始指令證據 | 結論 |
|---|---|---|
| `sub_4F6FF` `4F75D–4F784` | 讀 `ds:[byte_6FFC4×60 + i×2 − 5C96h]`，非零時寫入 runtime `[0x6742 + slot×2]` | 攻方 runtime 100 槽由省份參戰資料壓入，0 保留為空槽 |
| `sub_4F6FF` `4F816–4F83D` | 同形狀讀 `−5C82h`，寫入 runtime `[0x680A + slot×2]` | 守方 runtime 100 槽同樣是壓縮清單 |
| `sub_545B0` `545CD–545E6` | runtime `[0x6742 + i×2] × 21h + 7A7Dh` 後讀寫 runtime 記錄；`5464A–54663` 對 `[0x680A + i×2]` 同樣處理 | 每個非零 u16 是 1-based runtime 將領 ID，記錄大小 33 B |
| `sub_5446D` `5448A–544A3`、`544DC–544F5` | 逐一以兩張 runtime 100 槽表的值索引 `7A7Dh + ID×21h` | 兩側清單都走同一份將領記錄格式 |

要分清兩層：`.DT2`／`MEM_WAR.DAT` 的 `+68`／`+268` 先由 `sub_4F468` 讀入全域
緩衝 `word_6A8F4`／`word_6A9BC`，`sub_3964E` 再以相同偏移寫回；`sub_4F6FF`
則把省份資料建立成 live runtime 陣列 `0x6742`／`0x680A`。IDA 已證實 runtime
陣列的元素定位與 33-byte 記錄索引，但尚未證實每次檔案載入／寫回與 live 陣列的
同步時機。因此「將領 ID」是元素定位語意，不是宣稱每筆存檔快照已完成初始化；既有
8 個省的機器碼／填充殘料仍必須原樣保存，不可在 parser 層以劇本人數過濾。

**證據身分**：輸入 `WAR.EXE` SHA-256
`11dbfcf24686ab7765f788b38514cefd2039d0f60b6bd517d89fb5a84c068015`；工具
IDA Pro `9.4.0.260610`；位址空間為 IDA linear address；匯出檔
`workplace/ida/user-output/function-sub_4F6FF.txt`、`function-sub_545B0.txt`、
`function-sub_5446D.txt`、`function-sub_4F468.txt`、`function-sub_3964E.txt`。
未使用攤平 `.asm` 取代
`.i64` 函式邊界；匯出保留原始函式名、位址與運算元。

## 3. 目前的資料樣本說了什麼

`MEM_WAR.DAT` 是 39 × 469 的初始狀態，`SAVE(N).DT2` 同結構。

湖北（省 26）的初始記錄：

```
+0    1277, 7745, 1898, 26130
+8    FF ×10                    ← 全空
+18   FF ×10                    ← 全空
+28   46, 47, 75, 78, 80, 84, 0, 0, 0, 0
+48   127, 162, 0 ×8
+68   全 0（200 B）
+268  全 0（200 B）
+468  18
```

湖北的兩個 200 B 區全是 0，沒有部隊在場。

### ⚠️ 但 8 個省的單位區有未初始化的殘料

省 2、3、15、17、18、33、37、39 的 200 B 區**不是乾淨的 0**。
緬甸（省 39）那筆最明顯：

```
B[6]  1e 0e 1f ba ce 00 b8 00 25 cd 21 ba d5 00 b8 23 25 cd 21 ba
                          ~~~~~~~~ ~~~~~           ~~~~~~~~ ~~~~~
                          mov ax,0025h  int 21h    mov ax,2523h  int 21h
```

**這是 8086 機器碼**，不是遊戲資料。寫檔時把未初始化的記憶體一起寫進去了
——Turbo Pascal 的變數不會自動清零，1992 年的程式很常見。

其他幾省是 `ff ff ff ff` 之類的填充。省 3 的 `A[0]` 有一串看似規律的
`cc 00 89 00 39 00 ...`（u16 陣列），但既然同一個檔案裡確定有殘料，
**沒有辦法只從靜態資料分辨哪些是真資料**。

#### [記帳] 這一節原本寫成「39 省全部乾淨」

因為只看了湖北與河南兩個省。又一次「用少數資料點驗證自己」
（`docs/playtest/02` §6）。

後果是實質的：**不能拿 `MEM_WAR.DAT` 當戰前基準去 diff 出部隊欄位**，
那 8 個省會餵進垃圾。部隊欄位的語意要打進一場實際戰鬥、取戰鬥中的 `.DT2`
才驗得到。

### `+28` / `+48` = 攻守雙方的參戰單位 — **confirmed**

用將領記錄的所屬省欄位（`docs/spec/02` 附錄）交叉比對，河南那筆分得
乾乾淨淨：

| 欄位 | 河南（省 19）的內容 | 所屬省 |
|---|---|---|
| `+28` | 張學良、李寶章、李景林、萬福麟、韓麟春、許寶祥 | 1, 1, 11, 5, 2, 7 |
| `+48` | 李鴻翥、李鵬、袁家聲、米國賢、吳俊卿、張錦標、劉正芳 | 全部 19 |

`+28` 六個全是**張作霖系**（東北九省 + 河北）的外來將領，
`+48` 七個全是**河南本地**——攻方與守方。

程式碼那邊也對上：`sub_54CFD` 依 `byte_64901` 選用 `word_64902` 或
`word_64916` 其中一組（`docs/mechanics/30-combat.md` §3i），
而 `byte_64901` 正是「當前處理的是哪一方」。

#### 這解掉了先前的疑問

原本記「湖北只列 8 個而實機顯示將領數 15，對不上」。
**那從來就不是該省的將領名冊**，是參戰單位清單——一場戰鬥每方最多 10 個，
參戰的只是該省將領的一部分。

⚠️ 湖北那筆的兩組都是外省將領（江西、四川），不像河南那樣乾淨。
可能是殘料（`MEM_WAR.DAT` 有 8 個省帶未初始化資料，見下），
也可能是別的情況。以河南為準。

## 6. `sub_3964E` 的實際呼叫門檻 — **confirmed（IDA Pro 9.4）**

重新讀取 `WAR.EXE` 的 `sub_39B6E`、`sub_41D20`、`sub_41209` 與 `sub_4136B` 後，
寫回條件可以精確寫成：

1. `sub_41D20` 先跑 `sub_41209`；非二月回合數到 16、二月回合數到 15，或已有
   `byte_64901 != 0`，才會把 `byte_6A40A` 設成戰鬥結束。
2. 回到 `sub_39B6E` 後，只有「進入 `sub_41D20` 前 `byte_6A40A == 0`、該函式
   結束後 `byte_6A40A != 0`、而 `byte_64901 == 0`」這條分支才呼叫
   `sub_3964E`（`3A237–3A262`）。
3. `sub_4136B` 的補給見底會直接寫入勝方 `byte_64901 = 1/2`；`sub_4123D` 的
   雙方名單耗盡也直接寫入勝方 1/2。這兩種決勝結果不走上述 `sub_3964E` 分支。

因此「馮玉祥敗、吳佩孚勝」的正常戰報與立即撤退都沒有改寫 `MEM_WAR.DAT`，並不
矛盾；它們都沒有滿足「結束但未分勝負」的寫回門檻。下一個真正能驗證 +68／+268
的 oracle 應是**不分勝負地打滿回合上限**，再在 `sub_3964E` 寫回後取至少兩份
`MEM_WAR.DAT`／`.DT2` 快照。上述語意的輸入檔仍是本檔標頭的 `WAR.EXE` SHA-256，
工具為 IDA Pro 9.4；原始位址與原始函式名均保留。

未解 bytes；ID 錯誤也會失敗即關閉。

因此它只修正 remake 戰鬥副本與 `autosave()` 之間的資料遺失，不是原版
`sub_3964E` 的 `.DT2` 落盤重現。要把 live runtime 參戰清單接到檔案區塊，仍必須
先取得不分勝負打滿回合的正常 DOSBox 快照，並保留原始檔案雜湊、IDA 位址與 byte
差分；在那之前不得把此同步 API 當作 `+68`／`+268` 的語意證據。

## 9. 2026-08-10 DT1 layout 分支寫回界線

`.DT1` 戰爭記錄的兩個已確認 layout 現在可由
`internal/game.WriteWarRecordBranch` 逐筆寫回；它與本檔的 `.DT2` 寫回入口是兩個
不同契約，不能混用：

- `.DT2`／`MEM_WAR.DAT` 只寫已解出的戰鬥快照欄位；未解 runtime 同步保持原樣。
- `.DT1` writer 必須明確選 `WarRecordBranch4` 或 `WarRecordBranch8`，依證實偏移
  寫四個資源 word 與已提供的將領 ID 前綴；`+12h` union、未提供槽位與清除時機
  都不由 writer 猜測。

這只提升「已知 bytes 能安全寫回」的能力，不改變 §6 的原版 `sub_3964E` 呼叫門檻，
也沒有宣稱可由一次 remake 戰鬥自動重建兩個 layout。
