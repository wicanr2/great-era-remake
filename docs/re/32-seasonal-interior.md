## 2. 「兵多沒錢」旗標 — **confirmed**

主迴圈每一輪開頭先算一個旗標（`var_237`）：

```asm
cmp     [bp+var_234], 1         ; 兵力總和的高位字
jg      loc_1AD6E
jl      loc_1AD89
cmp     [bp+var_236], 86A0h     ; 低位字
jb      loc_1AD89
loc_1AD6E:
cmp     word ptr [di-6235h], 1388h   ; 省黃金 vs 5,000
jnb     loc_1AD89
mov     [bp+var_237], 1         ; ← 兵多但沒錢
```

`[-236h]:[-234h]` 又是**同一個 32-bit 兵力總和**（`docs/re/13` §3）：

```
(1 << 16) | 0x86A0 = 0x186A0 = **100,000**
```

所以旗標的語意是：

> **兵力總和 ≥ 100,000（5 個滿員步兵師）而且省黃金 < 5,000。**

目前只看到一個用途：**6 月不開發地價**。養不起兵的時候不投資土地——
很合理的優先序。

⚠️ 這是**第二個** 32-bit 兵力總和門檻（第一個是出兵閘門的 260,000，
`docs/re/30` §5d）。兩個都曾經被誤讀成「兩個獨立欄位各比一次」，
`CONTEXT.md` §5.26 記了那次訂正。**看到相鄰位址各比一次就要先想 32-bit。**

## 5. 對 remake 的意義

`cmd/dsds` 的電腦回合目前跑「遷都 → 決策鏈 A → 決策鏈 B」，
**內政整段沒接**。`sub_19563`（一年四次，佔比最大）已經解出來是徵兵，公式也定案了（§6）——
`花費 = min(省黃金 × 2/3, 步兵缺額 ÷ 10)`，夾難度上限。**可以接了**，
但實際加兵力的三支（`sub_18F10`／`sub_18F5B`／`sub_191A6`）還沒讀，
所以只能接「扣錢扣人口」那一半。

在那之前，已經可以照這張表接上**四條有明確動作的**：

```
6 月   人民忠誠度 +20
6 月   地價成長（地價 < 200 且不是「兵多沒錢」）
3/7/11 月  將領 +1 加 20
1/8/12 月  黃金支出
```

⚠️ 但**黃金支出接了卻不知道換到什麼**（`sub_19CD4` 與 `sub_197DB` 只看到
扣錢），單獨接上去會讓電腦白白變窮。**要等知道對價是什麼再接。**


## 6. `sub_19563` = **電腦的徵兵** — **confirmed**

一年跑四次（1／3／8／11 月），是內政裡佔比最大的一支。

### 五道門檻

```
if byte_6FE88 != 1 且 狀態[-2] != 1:   return    ; 兩道 gate（語意未解）

force  = sub_306CF(當前省)                        ; 兵力總和
upkeep = Round(force / 100) × 3                   ; **養兵成本 = 兵力的 3%**
if upkeep > 4,000: upkeep = 4,000                 ; 上限
spare  = 省黃金 − upkeep                           ; 可動用的餘裕

sub_18CD5(bp)                                     ; 設 狀態[-231h] = 1
if sub_13EA8(狀態, 省) < 3:  return               ; 某個計數 < 3
if 省黃金 < 500:             return
if spare ≤ 0:                return
if 狀態[-231h] != 0:         return               ; ← sub_18CD5 剛設過它

人口門檻 = 兵力總和 ÷ 100
if 人口(+12, 32-bit) < 人口門檻:  return          ; **人口撐不起這些兵就不徵**
if 人口 < 200:                    return
```

`Real(CX=87h SI=0 DI=4800h)` 解碼是 **100**（`tools/tp_real.py`），
所以養兵成本是 `兵力 ÷ 100 × 3` —— **兵力的 3%**，夾在 4,000 以內。

**人口門檻與養兵成本用同一個除數 100**：人口要撐得起兵力的 1%。

### 花多少：`sub_18D45` — **confirmed**

```
; 1. 步兵的總缺額（**只算兵種 1**）
count = 0; sum = 0
for g in 將領清單:
    if 將領[g].+21 == 1:  count++;  sum += 將領[g].+17
缺額 = count × 20,000 − sum

; 2. 預算 = 省黃金的 2/3
預算 = (省黃金 ÷ 3) × 2

; 3. 取小的
需要 = Round(缺額 ÷ 10)          ; ← **10 兵 = 1 金**
花費 = min(預算, 需要)

; 4. 難度上限
if byte_6FFCA & 0x10 或 & 4:  花費 = min(花費, 20,000)
else if byte_6FFCA & 0x20:    花費 = min(花費, 40,000)

; 5. 絕對上限
花費 = min(花費, 100,000)
```

⭐ **`10 兵 = 1 金` 對上了** `docs/mechanics/20-military.md` §5 記的玩家側比率
——兩側用同一個匯率。

⚠️ **只補步兵**。缺額只算兵種 1，砲兵／裝甲／騎兵的缺口不進這個公式。

⚠️ `byte_6FFCA` bit 4／bit 5 在這裡當**徵兵上限**用（20,000／40,000）。
那兩個位元先前只知道是「戰力加成」的一部分（`70-ai.md` §6c 的 bit 4–6），
**這是它們的第二個用途**。

### 扣費：`sub_194F4` — **confirmed（式子）**

```
省黃金 −= 花費
人口   −= Round(花費 ÷ 10)        ; Real(84h/0/2000h) = 10
```

合起來，一次徵兵：

```
花費   = 缺額 ÷ 10
人口減 = 花費 ÷ 10 = 缺額 ÷ 100
```

⚠️ **人口減少的量級對不上「一人一兵」**：補 20,000 兵只減 200 人口。
省的人口是六位數到八位數（湖北 18,250,000，畫面「1825 萬」，
`docs/spec/03`），所以這個扣除幾乎不影響人口。

這是**原版的行為**，照抄。可能的解釋（都未驗）：人口欄位的顯示單位與
內部單位不同、或設計上人口只是個軟門檻（§6 的「人口 ≥ 兵力 ÷ 100」
才是真正的限制）。**不要為了讓它「合理」而改比率。**

## 7. ⭐ `sub_18A67` = 「這個將領滿員了嗎」——四個滿員數的程式碼證據

`sub_19563` 開頭那道 gate（`狀態[-231h]`）是 `sub_18CD5` 算的：

```
狀態[-231h] = 1
for i = 1..將領清單長度:
    if !sub_18A67(狀態, 清單[i]):
        狀態[-231h] = 0                  ; ← 有人不滿足就清掉
        break
```

而 `sub_19563` 的條件是 `狀態[-231h] != 0 → 不徵兵`。合起來：

> **只要有一個將領不滿足 `sub_18A67`，就徵兵。**

`sub_18A67` 本身只有 71 行，內容是一張表：

```
兵種 = 將領[g].+21
兵力 = 將領[g].+17

兵種 1 → 兵力 ≥ 4E20h (20,000)
兵種 6 → 兵力 ≥ 2710h (10,000)
兵種 5 → 兵力 ≥ 00C8h (200)
兵種 4 → 兵力 ≥ 07D0h (2,000)
```

**這就是「這個部隊滿員了嗎」**，所以徵兵的觸發條件讀作：

> **只要有一個部隊沒滿員就徵兵。**

### 這解掉了 `CLAUDE.md` §1.5 掛著的兩件事

`CLAUDE.md` §1.5 原本記著：

> 兵種滿員數：步兵師 20,000、騎兵師 10,000、炮兵旅 2,000、裝甲部隊 200。
> 🔶 **只有 20,000 驗證通過**。其餘三個仍未驗，兵種欄位也還沒在將領記錄的
> 33 bytes 裡找到。

現在四個數字**全部**出現在同一支函式的四個 `cmp` 裡，而且與兵種編號綁在一起：

| `+21` | 滿員 | 兵種 |
|---:|---:|---|
| 1 | 20,000 | 步兵 |
| 6 | 10,000 | 騎兵 |
| 4 | 2,000 | 砲兵 |
| 5 | 200 | 裝甲 |

⚠️ 這**不是**第一個來源——`docs/spec/02` §4 早就用 `MAN(N).DAT` 三期的
最大值定過名。但那是**資料側**的觀察（「沒有一筆超過這個值」），
這裡是**程式碼側**的直接證據（「程式拿這個值當滿員判斷」）。
兩個獨立來源一致，這條可以從「強證據」升到 confirmed。

### ⚠️ 順帶推翻一個推導

`internal/game/strength.go` 的註解原本寫著「權重 1／10／100 與滿員數
20000／2000／200 成反比，三項吻合；但 4 對應的 5000 與社群說的騎兵 10000
對不上」，並據此拒絕定名。

現在知道**騎兵就是例外**：

```
兵種 1  權重 1    × 20,000 = 20,000
兵種 4  權重 10   ×  2,000 = 20,000
兵種 5  權重 100  ×    200 = 20,000
兵種 6  權重 4    × 10,000 = 40,000   ← 不一樣
```

三個乘積都是 20,000，騎兵是 40,000。**不要用「滿員 = 20000 ÷ 權重」
去推任何東西**——那個關係對騎兵不成立。


## 8. ⭐ `sub_18AED` = 徵兵的核心，**四個兵種匯率各不同** — **confirmed**

三支分配函式都呼叫它。簽名是 `sub_18AED(狀態X, &預算, 將領g)`
——**預算用指標傳進去，會被就地扣減**。

```
saved = *預算
if *預算 ≥ 2,000 (7D0h):        ; **單次上限 2,000 金**
    *預算 = 2,000
    夾過 = true

before = 將領[g].+17

兵種 1 步兵:  sub_5A467(&+17, *預算 × 10, 20,000);  *預算 −= 加量 ÷ 10
兵種 6 騎兵:  sub_5A467(&+17, *預算 ×  2, 10,000);  *預算 −= 加量 ÷ 2
兵種 5 裝甲:  sub_5A467(&+17, *預算 ÷ 10,    200);  *預算 −= 加量 × 10
兵種 4 砲兵:  sub_5A467(&+17, *預算 ÷  5,  2,000);  *預算 −= 加量 × 5

if 夾過:  *預算 = saved − 2,000 + *預算      ; 沒用完的還回去
```

`sub_5A467(ptr, delta, cap)` 是「加值並夾上限」。

### 匯率表

| 兵種 | 1 金買幾兵 | 滿員 | **徵滿要多少金** |
|---|---:|---:|---:|
| 1 步兵 | 10 | 20,000 | 2,000 |
| 6 騎兵 | 2 | 10,000 | 5,000 |
| 4 砲兵 | 1/5 | 2,000 | 10,000 |
| 5 裝甲 | 1/10 | 200 | 2,000 |

**單次上限 2,000 金剛好是徵滿一個步兵師**（20,000 ÷ 10）。

砲兵最貴（徵滿要 10,000 金），與它「遠程兵種」的定位（`docs/re/09`）相稱。

### 兩個關鍵細節

1. **夾到滿員之後只扣實際用掉的錢**——原版是先加、夾上限、再用
   「實際加了多少」反算花費。不是扣整筆預算。
2. **超過 2,000 的部分會還回預算**，讓下一個部隊接著用。
   所以一次徵兵可以補多個部隊。

### ⚠️ 這是電腦側的證據

玩家側走 `sub_28259`（`recruit.go` 的 `Recruit`），**兩者匯率是否相同未驗**。
目前只有步兵那一項在兩邊都對得上：實機畫面「黃金 4,150 → 上限 41,500」
＝ ×10 ＝ `sub_18AED` 的兵種 1。

`recruit.go` 的 `RecruitSoldiersPerGold = 10` 因此**只對步兵成立**，
其餘三個兵種用它會算錯。實作在 `internal/game/airecruit.go`
（`AIRecruitSoldiers`／`AIRecruitInto`），與玩家側分開。


## 9. ⭐⭐ 徵新兵的代價：`+19` 定名為**士兵戰技**

`sub_18F5B`（254 行）是三支分配路徑之一。前半是**依將領 `+0`（能力值）
降冪排序**清單，後半逐一補兵：

```
for i = 1..清單長度:
    g = 排序後的清單[i]
    if sub_18A67(X, g):  continue          ; 已滿員，跳過
    sub_18AED(X, &預算, g)                 ; 補兵
    已補 = true

    ; ⭐ **徵新兵的代價**
    if 將領[g].+20 ≥ 20 且 兵種 ∉ {4, 5}:
        將領[g].+20 −= 將領[g].+20 ÷ 4      ; **−25%**
    if 兵種 ∉ {4, 5}:
        將領[g].+19 −= 將領[g].+19 ÷ 5      ; **−20%**

    if 已補:  break                        ; ← **補一個就停**
```

**能力值高的將領優先補兵**，而且**一次只補一個部隊**。

### `+19` = 士兵戰技 — **confirmed（兩個獨立來源）**

`docs/spec/02` 把 `+19` 與 `+20` 記成「戰力公式用，語意未解」。`+19` 解了：

1. **練兵指令 `sub_1C916` 加的就是 `+19`**（`add [di+7A90h], cl`，
   `7A90h − 7A7Dh = 19`，`tools/field_writes.py` 掃出，過濾器經正對照）。
2. **那一支印的畫面文字是「司令欲練兵嗎？士兵戰技提升了！」**
   （`docs/re/27` §11）。

一支函式加它、畫面說那是「士兵戰技」——**`+19` 就是士兵戰技**。

而這裡徵新兵讓它 **−20%** 完全合理：**新兵拉低整體戰技**。

### `+20`：徵兵讓它 −25%，疑似「武裝程度」— **假說**

同一段對 `+20` 做 −25%，而且有一道門檻（`+20 ≥ 20` 才扣）。

`docs/re/27` §18 抓到的將領狀態畫面列了這些屬性：

> 帶兵能力／忠誠度／經驗／軍種／番號／士兵數／士兵攻擊力／**武裝程度**／
> 士兵戰技／體力／士氣

已定名的：`+0` 能力、`+17` 士兵數、`+19` 士兵戰技、`+29` 體力。
`+20` 在徵兵時下降，**「武裝程度」是最合理的候選**（新兵沒有裝備）——
但那是推論，**沒有直接證據**。要找到「加 `+20`」的地方才能定名。

### ⚠️ 砲兵與裝甲不受影響

兩道扣減都排除兵種 4（砲兵）與 5（裝甲）。那兩個兵種徵兵**不掉素質**——
與它們「徵滿要 10,000／2,000 金」的高單價相稱（`docs/re/32` §8）。


## 10. 三支分配策略 — **confirmed**

`sub_19443` 依序呼叫三支，各自有 `花費 > 0` 的前置，所以是**接力**：
前一支沒用完的預算留給下一支。

| 順序 | 函式 | 策略 |
|---:|---|---|
| 1 | `sub_18F10`（30 行）| 補**當前指定的那一個**（`X[-2]`），前置是 `花費 × 人力權重 < 20,000` |
| 2 | `sub_18F5B`（254 行）| 依將領 `+0`（能力值）**降冪排序**，補**第一個**沒滿員的就停 |
| 3 | `sub_191A6`（312 行）| **平分給最多 5 個**沒滿員的部隊 |

### `sub_191A6` 的三階段

```
; 1. 數沒滿員的部隊，**上限 5**
count = 0
for g in 清單:
    if !sub_18A67(X, g) 且 count < 5:  count++
if count == 0: return

; 2. 平分
每份 = Round(預算 ÷ count)

; 3. 逐一補，每個用「每份」當預算
for g in 清單:  ... sub_18AED(每份) ... 素質扣減 ...
```

**上限 5** 是硬編碼的（`cmp [bp+var_6], 5 / jge`）。

### 讀起來的意圖

三支合起來是一套**由專到廣**的分配：

```
先補指定的那一個  →  再補最強的那一個  →  剩下的雨露均霑（最多 5 個）
```

前兩支都是「補一個就停」，第三支才平分。所以錢多的時候一次徵兵可以
補到 7 個部隊（1 + 1 + 5）。
