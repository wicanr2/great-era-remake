## 1. 怎麼找到的

`WAR.EXE` 的畫面文字全是字模圖，`GRT.EXE` 那種「靠錯誤訊息定位功能」的捷徑用不上
（`docs/re/02` §4）。改用**資料檔的引用點**當錨——戰鬥一定要讀地圖與戰鬥狀態，
所以從 `warpos.dat`／`tername.dat`／`mem_war.dat` 的 XREF 往上追。

這比讀組合語言便宜，而且錨點是硬的：程式不會引用它不讀的檔案。

## 4. 雙磁碟路徑的差異

三個檔案的第二條路徑不一樣：

| 檔案 | 主路徑 | 備援路徑 |
|---|---|---|
| `warpos.dat` | `warpos.dat` | `b:warpos.dat` |
| `tername.dat` | `tername.dat` | `b:tername.dat` |
| `mem_war.dat` | `mem_war.dat` | **`a:mem_war.dat`** |

`mem_war.dat` 用 `a:` 而其他用 `b:`（`docs/re/01` §2 已注意到這點）。
`MEM_WAR.DAT` 是**戰鬥中會寫回**的檔案，而 `a:` 在雙磁碟機配置裡是
可寫的那一台——這解釋了差異，但**尚未從程式碼確認**。

`mem_war.dat` 有兩處引用（`sub_3964E` 與 `sub_4F468`），一處讀一處寫。

## 5. 對 M3 的意義

戰鬥系統是 M3 最大的一塊，也是目前完全未解的部分
（六角格移動、機動力、地形修正、戰損計算）。這份筆記把它從
「不知道在哪」推進到「知道從哪讀起」：

1. `sub_39B6E` 的 `+18F`–`+6F4` 是主迴圈。
2. 地形修正一定會讀 `tername.dat` 載入的陣列——
   從 `sub_4EFBE` 寫入的緩衝區往下追，就能找到 23 種地形編號怎麼被使用，
   這是 `docs/spec/01` §4 那個「地形語意未解」的解法。
3. 戰鬥狀態的結構 = `MEM_WAR.DAT` 的 469 B × 39，
   與 `SAVE(N).DT2` 同結構（`docs/re/03` §3.5）。

## 5A. 找六角格移動：兩條走不通的路（記帳）

社群資料說「數字鍵 1–6 對應六個方向移動游標與部隊」（`CLAUDE.md` §1.5），
所以先找 `'1'`–`'6'` 的按鍵比較。

### 路徑 A：`cmp al, 31h`–`36h` → 是選單，不是方向鍵

行 76045–76230 有 `'1'` 到 `'6'` 的連續六個比較，間隔規律，看起來很像六方向分支。
**但不是。** 每個分支做的事是把一組座標傳給 `sub_5A4BC`：

```
'1' → (0F3, 72) .. (102, 7C)
'2' → (0F3, 62) .. (102, 6C)
'3' → (0F3, B5) .. (102, BF)
'4' → (0F3, A3) .. (102, AD)
'5' → (0F3, F4) .. (102, FE)
```

x 固定在 `0F3`–`102`（243–258），y 逐項不同——**這是選單項目的高亮框**，
所屬函式 `sub_38DFE` 是選單 UI。

### 路徑 B：`sub_39B6E` 的按鍵處理 → 是狀態機

戰鬥主函式裡有 4 個 `KEYPRESSED`，但它的比較是 `cmp al, 8` / `4` / `2` / `1`——
**位元遮罩，不是 ASCII 按鍵值**。這一層是狀態機，實際的輸入解讀在更下層。

### [雷] IDA 對 Turbo Pascal 的 sp-analysis 會失敗

`sub_38DFE` 那段反組譯出來是連續好幾個 `mov ax, N` 中間沒有 `push`，
但 Turbo Pascal 傳參數就是靠 push——**指令沒被完整解析出來**。
`WAR.EXE` 的進入點也標了 `sp-analysis failed`。

讀這支的組合語言時要記得：**看到不連貫的指令序列，先懷疑是 IDA 沒解析好，
不要當成程式邏輯去推**。必要時得手動修 stack frame 或改用其他工具交叉驗證。
