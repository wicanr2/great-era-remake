## 1. 結構：每省 392 B = 196 個 u16

`WAR.EXE` 的 `sub_4ED9B` 是讀這個檔的函式，反組譯直接給出答案：

```
Assign(f, 'nwmap.dat')
Reset(f, 188h)                  ← recsize = 392
Seek(f, byte_6FFC4 - 1)         ← 省編號 - 1
Read(f, byte_64946)             ← 讀一筆 392 B
Close(f)
```

392 = 196 × 2，而 196 = 14 × 14——與 `WARPOS.DAT`／`TERNAME.DAT` 同一張格子圖，
**每格一個 u16**。省的定位是 `Seek(省編號 - 1)`，1-based 轉 0-based。

39 筆用掉 15,288 B，檔案 15,360 B 多出 72 B。Turbo Pascal 的 typed file 不在乎
檔尾多餘的 bytes，所以這 72 B 是尾料，不是記錄的一部分。

> `docs/re/03` 曾記「15,360 / 392 = 39.18 不整除，recsize 可能抓錯」。
> recsize 沒抓錯，是「檔案大小必須整除」這個預期不對。

## 2. 每格 u16 的拆法

```
bit 15-12   旗標（4 個 bit，語意未解）
bit 11-0    地物編號
```

### 地物編號 1–22 = `NEWTERR.TPC` 的圖塊（1-based）

`NEWTERR.TPC` 正好有 22 張 32×24 圖塊，編號減 1 就是圖塊索引。

| 編號 | 格數 | 圖塊 | 依據 |
|---:|---:|---|---|
| 1 | 1,399 | 平原 | 最多；`TERNAME` 無地名的格子多半是 1 |
| 2 | 1,515 | 丘陵 | 山地名的格子用 2 或 6 |
| 3 | 1,385 | 水 | 湖北的長江 33 格、漢水 10 格**全部是 3** |
| 4 | 426 | 森林 | |
| 5 | 91 | 城市 | **39/39 驗證**，見 §3 |
| 6 | 722 | 高山 | |
| 7 | 136 | 沙漠／黃土 | |
| 8 | 22 | 橋（縱）| |
| 9 | 16 | 橋（橫）| |
| 10 | 947 | 岩地／荒地 | |
| 11 | 8 | 關隘城門 | 數量少，符合關隘 |
| 12–22 | 1–29 | 城牆各段（橫、縱、彎角、斜坡）| 只出現在北方幾省，符合長城 |

12、13、14、20 各只有 1 格，21 有 2 格——城牆組件本來就是零星拼接的。

### 大於 22 的是鐵路，編碼是 `30 + 25×圖塊 + 地形`

885 格、57 種值，全部落在 `TERNAME` 標為「◯◯鐵路」的格子上。拆法：

```
鐵路圖塊 = (v - 31) div 25     0..20，對應 RAIL.TPC 的 21 張
底層地形 = (v - 31) mod 25 + 1  1..22，照常查 NEWTERR
```

`25` 是 stride，比地形數 22 多 3 個空號。

### 這個公式怎麼確立的

先注意到 `(v-31) mod 25` 只有 5 個值 `{0, 1, 2, 6, 9}`。加 1 之後是
`{1, 2, 3, 7, 10}`——正好是平原、丘陵、水、沙漠、岩地，**鐵路會經過的地形**。
水的那 77 格就是鐵橋。

另一半 `(v-31) div 25` 的值域是 `0..20`，21 個值，而 `RAIL.TPC` 正好 21 張。

兩邊獨立對上，而且全 39 省 7,644 格拆下來零例外（測試
`internal/game/tile_test.go` 的 `TestTileKindRanges`）。視覺驗收也通過：
湖北的鐵路連成連貫路網、穿過五座城市、跨長江處是鐵橋；河北的長城橫貫北緣，
鐵路網連接關內各城。

### `RAIL.TPC` 是 4-bit chunky，不是 BGI

副檔名雖然是 `.TPC`，但格式完全不同——檔頭讀出來是 1×1，用 BGI 的 plane
佈局解會得到雜訊。它是每 byte 兩個像素（高 nibble 在左）的 chunky，
一列 16 bytes = 32 px：

```
8,064 = 21 張 × (32 × 24 ÷ 2)
```

整個檔案只有 7 種 byte 值，nibble 只有 `{0, 7, 8}`——透明、淺灰、深灰。
索引 0 透明，疊在地形圖塊上。21 張分別是縱、橫、四種彎角、T 字接、
十字接與車站。

## 3. 城市：39/39 零誤差

把每省「地物編號 == 5」的格數，對上 `TOWN(1).DAT` 的城市數欄位（`+16`）：

**39 個省全部吻合。**

湖北是 5 格 = 漢口、武昌、漢陽、襄陽、宜昌，實機政略畫面顯示「城市數 5」。
交叉比對 `TERNAME` 的地名索引，這 5 格正好落在那 5 個城市地名上。

這條同時驗證了三件事：`NWMAP` 的記錄切法、地物編號 5 是城市、
以及 SPEC-03 的 `+16` 是城市數。

## 4. 旗標（bit 15–12）：未解

| 旗標 | 格數 |
|---|---:|
| 無 | 6,462 |
| `0x4000` | 584 |
| `0x8000` | 362 |
| `0x1000` | 185 |
| `0x2000` | 51 |

已知的兩件事：

- **城市（編號 5）永遠帶旗標**，91 格全部有：`0x4000` 60 格、`0x2000` 31 格。
  沒有一個城市是無旗標的。
- 編號 6（高山）、7（沙漠）的 858 格**完全沒有旗標**。

### [記帳] 差點把 `0x4000` 當成兵工廠

湖北有 3 個帶 `0x4000` 的城市，而實機「兵工廠數 3」——看起來完美。
但推廣到 39 省只有 9 個省吻合，**是巧合**。

這正是 `docs/playtest/02` §6 記過的「用同一個資料點驗證自己，永遠會過」。
省下的成本很低（一次全省掃描），漏掉的代價是把巧合寫成規格。

`0x2000` 有 31 個城市帶，接近但不等於省數 39，所以也不是「省會」。

## 5. remake 的用法

`TERNAME` 給地名、`NWMAP` 給地物類型，兩張表疊起來才是完整的戰場：
「這一格是長江，畫水」「這一格是漢口，畫城市」。

畫法是兩層：先用地形編號取 `NEWTERR.TPC` 的圖塊鋪底，
有鐵路的格子再疊一張 `RAIL.TPC`（索引 0 透明）。
實作在 `internal/ui/render/tileset.go`。
