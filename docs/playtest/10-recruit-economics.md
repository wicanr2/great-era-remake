# 徵兵的成本與上限：10 兵 = 1 黃金

日期：2026-08-01
路徑：政略指令 **5 徵兵** → 1 徵兵 → 1 徵步兵 → 輸入數量
存檔：進度一（`SAVE(1)`），載入後過了一個月

`docs/playtest/09` 的端到端實跑暴露「規則層只有消耗沒有補充」。
徵兵是原版五條補充管道裡最直接的一條，這一輪把它量出來。

---

## 1. 選單結構

```
指令 5「徵兵」
  ├ 1. 徵兵          → sub_29B46
  └ 2. 重新整編      → sub_29DDF
       ↓（選 1）
  1. 徵步兵    2. 徵裝甲兵
  3. 徵砲兵    4. 徵騎兵
       ↓
  司令，欲徵多少步兵？ (0-41500)
       ↓（輸入 1000）
  共須黃金 100
  司令，您確定嗎？ (Y/N)
```

**「重新整編」**印證了 `CLAUDE.md` §1.5 的社群說法
「另有整編可在部隊間分配兵力」——它確實存在，是徵兵選單的第二項。

⚠️ 兵種的**選單順序**（步兵／裝甲兵／砲兵／騎兵）與**兵種編號**
（步 1、砲 4、裝甲 5、騎 6）不同。UI 用前者，規則層用後者。

## 2. ✅ 10 兵 = 1 黃金 — confirmed（兩個樣本 + 一次計算）

| 省 | 黃金 | 畫面的上限 | 比值 |
|---|---:|---|---:|
| 湖北（26）| 4,150 | `(0-41500)` | **×10** |
| 河南（19）| 5,950 | `(0-59500)` | **×10** |

再輸入 1,000 步兵：

```
司令，欲徵多少步兵？   (0-59500)      1000
共須黃金  100
```

`1000 ÷ 10 = 100` ✓

**兩個獨立樣本的上限 + 一次實際計算，零誤差。**

### 對照反組譯

`sub_28259`（徵兵執行，630 行）末尾：

```asm
mov     ax, [di+7A8Eh]          ; 將領 +17 兵力
...
mov     [di+7A8Eh], cx          ; 寫回兵力
...
sub     [di-6235h], cx          ; 省份 +0 黃金 -= cx
```

減黃金的動作對得上，`cx` 的算法（÷10）在中間那段 Real 運算裡，
**還沒逐行讀**——但實機已經把答案印在畫面上了。

## 3. 分配規則只解了一半

`sub_28259` 掃該省將領時檢查五個條件：

```asm
cmp     byte ptr [di+7A92h], 5      ; +21 兵種
mov     al, [di+7A81h]              ; +4  所屬省
cmp     byte ptr [di+7A8Dh], 1      ; +16 可用 == 1
cmp     word ptr [di+7A8Eh], 0C8h   ; +17 兵力 vs 200（裝甲兵滿員）
mov     ax, [di+7A8Bh]              ; +14 勢力
```

**「補到滿員為止、只補同兵種」**是清楚的。
沒解的是**補的先後次序**——那會決定誰先補滿。
規則層照將領清單的順序補（攻擊力降序，`docs/re/13` §1），
標為 remake 差異。

## 4. 進了規則層

`internal/game/recruit.go`：

```go
const RecruitSoldiersPerGold = 10

func (w *AIWorld) RecruitLimit(p ProvinceID) int      // 黃金 × 10
func RecruitCost(n int) int                           // n ÷ 10
func (w *AIWorld) Recruit(p, branch, n) (int, error)  // 補到滿為止
func (w *AIWorld) RecruitToFull(p, branch) int        // ← remake 的便利函式
```

`RecruitToFull` **原版沒有**（原版一次只徵一個兵種、玩家輸入數量），
它存在只是為了讓 `cmd/aisim -recruit` 的長跑不會枯竭。標為 remake 行為。
