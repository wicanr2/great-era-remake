# `.GLB` / `.GTB` — 256 色圖庫與目錄

> 狀態：**confirmed**（逐像素 round-trip 通過原版實機畫面）
> 驗證對象：`GRT.GLB`(239,732 B) / `GRT.GTB`(208 B)、`GRT2.GLB`(138,660 B) / `GRT2.GTB`(377 B)
> 工具：`tools/dcl.py`（DCL 解壓）、`tools/glb.py`（解包）
> 日期：2026-08-01

---

## 1. 結論先講

`.GLB` 是遊戲的 **256 色圖庫**，`.GTB` 是它的目錄。這解開了兩件事：

1. **開場動畫與標題那些 256 色美術存在哪裡**——`CLAUDE.md` §3.2 實測發現遊戲在
   標題階段是 mode 13h 320×200 256 色，但 `.TPC` 是 4-plane 16 色，裝不下這些圖。
2. **`GRT.GLB` 熵 7.96 bit/byte 的高熵是什麼**——不是加密，是 PKWARE DCL implode 壓縮。

兩個檔合計 45 筆，41 張圖 + 4 個調色盤，全部解出，零失敗。

---

## 2. `.GTB` 目錄格式

每筆固定 **13 bytes**，檔案大小整除 13（208/13 = 16、377/13 = 29）。

| 位移 | 型別 | 內容 |
|---|---|---|
| +0 | u8 | flag：`0` = 調色盤，`1` = 圖像 |
| +1 | u16 | `raw_size` 解壓後大小。圖像 = `w × h`，調色盤固定 768 |
| +3 | u16 | `comp_size` 壓縮後大小 |
| +5 | u32 | `offset` 在 `.GLB` 內的位移 |
| +9 | u16 | `width` |
| +11 | u16 | `height` |

三條自洽性檢查全部通過，這是格式判定的依據：

- `offset[n] + comp_size[n] == offset[n+1]`，逐筆成立
- 最後一筆的 `offset + comp_size` 落在 `.GLB` 大小之內
- `raw_size == width × height`，41 張圖全中（例如 `0xfa00` = 64000 = 320×200、
  `0x213b` = 8507 = 47×181）

**每像素 1 byte**，所以是 256 色 chunky，與 `.TPC` 的 4-plane planar 完全不同。

---

## 3. `.GLB` 壓縮：PKWARE DCL implode

每一筆各自是一段**獨立完整**的 DCL stream，不是整個檔案一段。45 筆的起點
前兩個 byte 全部是 `00 06`——DCL 的 header：

| byte | 值 | 意義 |
|---|---|---|
| +0 | `00` | literal 不編碼（字面值直接 8 bits，不走 Huffman） |
| +1 | `06` | 字典 4096 bytes |

演算法是公開的（zlib contrib 的 `blast.c`），`tools/dcl.py` 是它的 Python 移植，
**沒有從遊戲反組譯任何東西**。用 `blast.c` 附的官方測試向量驗證過：

```
輸入 00 04 82 24 25 8f 80 7f  →  "AIAIAIAIAIAIA"   PASS
```

### [雷] Huffman 碼是 bit-inverted

`blast.c` 的 `decode()` 裡是 `code |= (bitbuf & 1) ^ 1`。漏掉那個 `^ 1`，
**literal 仍然解得出來**（走的是 raw 8 bits 那條路），但一遇到 length/distance 對
就會算出離譜的距離，症狀是「解到第 2–28 個 byte 就爆」。
這個錯很容易誤判成「格式猜錯了」而放棄整條路線。

DCL 的位元序是 LSB-first，別套 DEFLATE 的直覺。

---

## 4. 調色盤

flag = 0 的那幾筆是調色盤，解出來固定 **768 bytes = 256 × RGB**，
值域 0–63（VGA DAC 是 6-bit）。實測四個調色盤的最大值**正好是 63**，
這是格式判定的強證據——錯誤的解壓演算法不可能讓 768 個值全落在 0–63。

調色盤與圖像在 `.GLB` 內**交錯排列**，一個調色盤管到下一個調色盤出現為止：

| 檔案 | 調色盤位置 | 管轄範圍 |
|---|---|---|
| `GRT.GLB` | #0、#2 | #1 用 #0；#3–#15 用 #2 |
| `GRT2.GLB` | #0、#12 | #1–#11 用 #0；#13–#28 用 #12 |

### [雷] 6-bit → 8-bit 要用位元複製，不是比例縮放

```
正確： (v << 2) | (v >> 4)      16 → 65    51 → 207   63 → 255
錯誤： v * 255 // 63            16 → 64    51 → 206   63 → 255
```

兩者只差 1，但逐像素比對原版截圖時，**這個 1 會讓整張圖判定為不同**
（實測相異率 99.99%，看起來完全像是「解錯圖」）。
這是 VGA 6-bit DAC 轉 8-bit 的標準做法：把高位重複填進低位。

---

## 5. 透明色

圖像的**索引 0 是透明色**。`GRT.GLB` #15（書法標題）只有三個索引值 `0, 11, 74`：
0 是透明、11 是暗色描邊、74 是紅色主體。疊圖時索引 0 的像素不寫入，露出底圖。

---

## 6. 驗證：逐像素 round-trip

`CLAUDE.md` §5 步驟 3 要求「與原版截圖逐像素相同才算數」。用書法標題
（`GRT.GLB` #15，47×181）對 DOSBox 實機畫面驗證：

**第一步——定位，且不依賴調色盤。** 在 320×200 畫面內窮舉所有可能位置，
檢查「同一個索引值的所有像素在截圖裡是否都是同一種顏色」。這個判準與調色盤無關，
5,000+ 個候選位置中**只有一個通過**：`(259, 13)`。兩張獨立截圖給出相同位置。

**第二步——逐像素比對。**

| 截圖 | 非透明像素相異 | 結果 |
|---|---|---|
| `03-later` @(259,13) | **0 / 4,005** | 完全相同 ✓ |
| `20-title` @(259,13) | **0 / 4,005** | 完全相同 ✓ |

全區 8,507 個像素中相異 4,502 個，正好等於索引 0 的透明像素數
（8,507 − 4,005 = 4,502）——它們顯示的是底圖，本來就該不同。

驗證鏈完整閉合：格式解析 → DCL 解壓（官方測試向量 + 45/45）→ 調色盤 6-bit 合法
→ 轉換公式 → **與原版實機畫面逐像素相同**。

## 7. 內容

| 檔案 | 筆數 | 內容 |
|---|---:|---|
| `GRT.GLB` | 16 | 320×200 開場美術 ×5、260×140 ×2、書法標題「大時代的故事」(47×181)、47×28 小圖 ×5 |
| `GRT2.GLB` | 29 | 237×200 人物插圖 ×4（軍官配青天白日旗）、320×74 條幅 ×4、168×51、124×46、186×77 等 |

`GRT.GLB` 的日期是 **1992-09-26**、`GRT2.GLB` 是 **1992-10-13**（見
`docs/formats/03-placd-archive.md`），都早於資料主體的 1993-01-10——
發行時就凍結的美術，後續更新沒有再動。

解出的圖在 `workplace/glb-out/`（**不進版控**，是原版美術）。
