# `.15` 字模檔與文本儲存機制

> 狀態：**強證據**（51 檔全量比對通過，但槽寬與繪製語意尚未經反組譯確認）
> 驗證對象：`workplace/orig/game/` 的 51 個字模檔
> 工具：`tools/glyph_lookup.py`、`tools/glyph_slots.py`
> 日期：2026-08-01

---

## 1. 結論先講

《大時代的故事》的中文**不經過索引表**。字模序列本身就是文本：

```
檔案 = [字模0][字模1][字模2] …          每個字模 30 B，16×15 點陣
       └────── 詞條 0 ──────┘└─ 詞條 1 …   每 w 個字模 = 一個詞條，w 依檔案固定
```

想畫第 k 個詞條，程式從 offset `k × w × 30` 讀 `w × 30` bytes 直接送 BGI `putimage`。
不需要碼點、不需要查表，也因此 Big5 grep 命中數是零——**原始碼裡本來就沒有碼點**。

字模全部來自倚天中文系統的 16×15 字庫。6,174 個字模逐 byte 比對，
**只有 1 個不是倚天原樣**（見 §5）。

---

## 2. 字模格式

| 項目 | 值 |
|---|---|
| 尺寸 | 16 × 15 |
| 每列 | `(16+7)/8` = 2 bytes，MSB-first |
| 每字 | 2 × 15 = **30 bytes** |
| 排列 | 由上而下，無檔頭、無對齊填充 |

與倚天 `STDFONT.15` / `SPCFONT.15` 同格式，可直接互換。

---

## 3. 定長槽位（這個格式的核心）

詞條長度固定為 `w` 個字模，不足的格子填**全零字模**（空白）。空白有兩種語意，
不可混為一談：

### 3.1 排版填充

`w` 格放不滿時補空白，對齊方式**依檔案而異**，同一檔內一致：

| 對齊 | 例 | 出現在 |
|---|---|---|
| 靠左 | `齊齊哈爾␣`、`呼蘭␣␣␣` | `TN15.N` 地名（全 39 檔） |
| 靠右 | `␣寺內壽一` | `JAPAN1/2.15` 日本將領名 |
| 分散 | `劉␣驥`、`蒙␣古` | `MAN*` 將領名、`3.15` |

分散對齊是原版真實的排版，不是解析誤差——兩字姓名攤在三格中間留空，
在名冊畫面上與三字姓名對齊。

### 3.2 執行期數字佔位

`FAN(2).15` / `FAN(3).15` 的空白在詞條**中間**，是留給番號數字的：

```
第 ␣ 集 團 軍     →   第 三 集 團 軍
騎 兵 第 ␣ 軍     →   騎 兵 第 一 軍
第 ␣ ␣ 戰 區     →   第 一 二 戰 區
```

填進去的數字字模來自 `1.15`（開頭就是全形 `１２３４５６７８９０`）。
這是全專案目前唯一觀察到的「索引式取字」用法。

**槽寬依據**分兩級，不可混用：

- `content`（5 檔）：檔案沒有空白（或空白在中間），排版模式推不動，

`3.15` 的順序，要從執行檔載入 `TN15.%d` 的那段確認）。

全部詞條在 `docs/formats/glyph-tables/`（`_slots.json` 含完整詞條，
每檔另有 `<name>.json` 的逐字模字表）。

## 5. 例外記帳

全量 6,174 個字模，反查結果：

| 類別 | 數量 | 說明 |
|---|---:|---|
| 倚天字庫直接命中 | 4,799 | byte-identical |
| 全零（空白填充） | 1,374 | 排版或數字佔位，非缺字 |
| 不在倚天字庫 | **1** | 見下 |

唯一的例外是 `1.15` 的第 12 個字模：

```
遊戲 #12                    倚天「，」(A141)
      ████                        ████
    ████████                    ████████
    ████████                    ████████
      ████                        ████
      ██                          ██
    ██                          ██
  ██                          ██
```

以二維位移窮舉比對，確認它是**倚天「，」左移 3 px、下移 2 列**的版本，
位移後 byte-identical。遊戲把逗號改畫在字格左下角。

也就是說：**這套字模 100% 出自倚天字庫**，沒有任何自製字形。

## 5b. 反查在原理上不會取錯字 — **confirmed**（2026-08-01）

字模反查是 byte-exact 比對：拿 30 bytes 去倚天字庫找完全相同的那一格。
這種比對有一個看不見的風險——**只要字庫裡有兩個 Big5 碼點共用同一個字形，
反查就永遠取到排前面的那個**，後面那個碼點會系統性地被遮蔽。
症狀是「查得到，但是錯字」，比查不到還難發現。

`tools/dup_glyph.py` 把它量出來了：

```
STDFONT.15: 392820 B → 13094 字
非空白的重複字形組數: 0
被遮蔽的碼點數: 0（0.00%）
```

**13,094 個字形裡，沒有任何兩個共用同一組 30 bytes。**
所以反查是單射的，取不到錯的碼點。

### 這條驗證換來什麼

`docs/reference/people/02-status.md` 整理將領名冊時發現 **22 筆**
遊戲寫法與通行寫法不同（閰錫山／閻錫山、龐炳勛／龐炳勳、周爛／周斕、
謬培南／繆培南…）。當時有兩種解釋：

1. 反查取錯了字
2. 1992 年輸入時就是那樣寫的

**第 1 種已排除。** 那 22 筆是**原版的文本事實**——當年真的打了「閰」。

⚠️ 對 remake 的意義：繁中母本要**保留原版寫法**（保存專案的本分），
英文與日文版才用通行寫法。`translations/glossary.md` 兩欄都要留。

⚠️ 這條只證明「反查不會取錯」，**不證明「字模一定來自倚天」**——
後者是 §5 的例外記帳在管的（51 檔 6,174 個字模，倚天命中 4,799、
空白 1,374、例外 1）。兩者互補。

## 6. 這件事對專案的意義

### 推翻了原本的假說形狀

`CLAUDE.md` §3.5／§5 原本假設「文字以第 N 個字模的索引儲存，畫面上的中文是查表畫出來的」。
實際情況更直接：**文字就是字模本身**，沒有中間那層索引。原假說的還原鏈是

```
字模檔 → 倚天反查 → Big5 ←── 索引序列（要從反組譯找出來）
```

實際只需要前半段：

```
字模檔 → 倚天反查 → Big5 → 依槽寬切開 → 原文
```

`CLAUDE.md` §5 步驟 2「索引來源」對這 51 個檔案**不適用**。

### 2026-08-01 補：索引那一層確實存在，只是不在資料檔裡

上面那句「沒有中間那層索引」講的是**檔案內部**——`.15` 檔本身確實不含索引。
但畫面上要印哪一個詞條，還是得有人指定，那個指定就是索引。

`docs/re/24` 找到它了：**索引是編譯進 `WAR.EXE` 的立即數**，
寫在每個繪字呼叫點上，**1-based**。

```
畫字呼叫點的立即數（WAR.EXE）──▶ .15 詞表的第 N 條 ──▶ 已還原的 Big5
```

`tools/glyph_calls.py` 把 924 個呼叫點全部解出來了。所以 §5 的還原鏈
步驟 2 不是「不適用」，而是**答案在執行檔而不在資料檔**——
原本畫的圖找錯地方了。

同時驗到「一次畫幾個字」的四支函式與詞表槽寬一一對應，
本文件 §4 靠空白排版推出來的槽寬，拿到了程式碼側的獨立佐證。

### 但還原鏈沒有走完

這 51 檔是**詞表**——地名、人名、番號、UI 詞彙。遊戲的敘事文本（事件、新聞、劇情）
不在裡面。候選位置：

| 檔案 | 大小 | 線索 |
|---|---:|---|
| `NEWSDATA.DAT` | 29,784 | 名字像新聞文本；**不整除 30**，所以不是純字模，可能才是真正的索引流 |
| `GRT2.GLB` | 138,660 | **整除 30**（= 4,622 字模），可能是字模封裝 |
| `GRT.GLB` | 239,732 | 熵 7.96 bit/byte，壓縮或加密 |

### 順帶解開的線索

`MAN115` 有 274 位將領，`MAN(1).DAT` 是 9,042 B —— **9042 ÷ 274 = 33，整除**。
極可能是每位將領 33 bytes 的屬性表。`MAN(2).DAT`／`MAN(3).DAT` 同為 9,042 B，
但 `MAN215`／`MAN315` 只有 106 個名字，兩者對不上（可能是固定 274 筆的陣列，
後段未用）。**待驗。**

### 對 remake 的影響

原版的定長槽位 + 空白填充是磁片時代的產物，remake 不沿用（`CLAUDE.md` §6）。
但兩件事要保留：

1. **倚天字形**：remake 的中文呈現直接用 `STDFONT.15`／`SPCFONT.15`，
   與原版同一族字形，不做 TTF rasterize。
2. **分散對齊**：兩字姓名攤在三格的排版是原版的視覺特徵，呈現層要重現。
