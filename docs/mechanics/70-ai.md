# 機制：電腦 AI 的判斷邏輯

依 `CLAUDE.md` §6.5，這是機制文件裡優先度最高的一份——
remake 之後要調難度、改進電腦對手、或做強化 AI，全靠這裡。

推論等級的定義見 `00-index.md`。

---

## 1. 勢力輪替：主迴圈逐省處理 — **confirmed**

`WAR.EXE` 的 `PROGRAM`（`docs/re/06`）是一個以 `byte_6FE89` 為迴圈變數的大迴圈，
**變數代表當前處理到第幾個省**。每一輪對該省跑一串 gate，決定要走哪條路。

也就是說，遊戲的推進單位是**省**，不是「勢力」——電腦不是「每個勢力想一次」，
而是「每個省被輪到時判斷一次」。這對 remake 的 AI 設計是關鍵前提：
原版的決策粒度在省，改成勢力層級的全局規劃會是**行為改動，不是還原**。

驗證位址：`PROGRAM` 的 `loc_10C18`（迴圈頭）、`loc_11002`（戰鬥 gate）。

---

## 2. 「這個省要不要進戰鬥」的三個條件 — **confirmed**

```asm
loc_11002:
        mov     al, byte_6FE89      ; 當前省
        mov     dx, 25h             ; ×37 = 省份記錄大小（SPEC-03）
        mul     dx
        mov     di, ax
        push    word ptr [di-6221h] ; 省份記錄裡的一個 word
        call    sub_5C7FE
        or      al, al
        jnz     loc_1102C           ; 1. 成立 → 進戰鬥
        cmp     byte_7003A, 0
        jnz     loc_1102C           ; 2. 成立 → 進戰鬥
        cmp     byte_7003B, 0
        jnz     loc_1102C           ; 3. 成立 → 進戰鬥
        jmp     loc_11143           ; 都不成立 → 這個省跳過
```

三個條件是 **OR**，任一成立就打。

### 條件 1：司令是不是十大勢力之一（`sub_5C7FE`）

```
sub_5C7FE(arg: word) -> boolean
    if byte_7003A != 0:  return false
    if arg == 0:         return false
    for i = 1 to 10:
        if arg == 表[i]: return true
    return false
```

**在一個 10 元素的 word 表裡線性搜尋**。第一期正好有 10 個勢力
（張作霖、孫傳芳、吳佩孚、蔣中正、劉湘、唐繼堯、袁祖銘、趙恆惕、閰錫山、馮玉祥，
見 `docs/spec/03` §3），而傳進去的 word 來自省份記錄，司令欄位存的正是將領 ID。

- 迴圈從 **1** 數到 10，不是 0——與將領 ID 是 1-based 一致（SPEC-03 §3）。
- `arg == 0` 直接回 false，對應「無主的省」。

**傳入的是司令 ID 已經是 confirmed**——§5 從另一條路（`sub_3964E` 用同一個
基址讀 `+20`、寫 `+0`／`+2`）交叉印證了這一點。

⚠️ 但**十大勢力表本身的內容是執行期填的，靜態看不到**。
「表裡裝的就是那十位領袖」仍是從「10 這個數字 + 傳入的是司令 ID」推的
**強證據**，要完全確認得動態 dump 或找到填表的程式碼。

### 條件 3：`byte_7003B` 是「觀戰」開關 — **confirmed（程式碼）／強證據（語意）**

`byte_7003B` 全 `WAR.EXE` **只有一個寫入點**：`sub_1BF58`，而那是個 toggle：

```asm
cmp     byte_7003B, 0
mov     al, 0
jnz     short loc_1C04B
inc     ax                      ; 0 → 1
loc_1C04B:
mov     byte_7003B, al
... 畫一個框 ...
cmp     byte_7003B, 0
jz      short loc_1C08B
OUTTEXTXY(..., "ON")            ; 開
jmp     short loc_1C09D
loc_1C08B:
OUTTEXTXY(..., "OFF")           ; 關
```

**輸出 ON/OFF 字串的設定開關**。`sub_1BF58` 由 `sub_1C38C` 呼叫，
是設定選單的一項。

配合 `2.15` 詞條 147「**觀戰**」，方向相反的謎就解開了：

| 位置 | 開關打開時 | 讀起來 |
|---|---|---|
| `sub_5C7FE` 開頭 | return false | 「這個省不算我的勢力」|
| 主迴圈 gate | 進戰鬥 | 「但還是要進去看」|

**觀戰模式：不是自己的省也進戰鬥畫面**。兩處行為完全自洽。

⚠️ 語意標**強證據**而非 confirmed——ON/OFF 開關與 toggle 行為是讀到的，
「這個開關叫觀戰」是從詞表與兩處用法推的，沒有直接讀到標籤字模。

### 條件 2：`byte_7003A` — **未知**

只在 `PROGRAM` 初始化時設 0，**全檔沒有其他寫入點**。
所以在正常流程下它恆為 0，這個條件永遠不成立——可能是開發期的 debug 旗標。

`sub_5C7FE` 開頭也檢查它（非 0 直接 return false），與 `7003B` 同樣的用法。

## 3. 進戰鬥前會釋放政略階段的記憶體 — **confirmed**

`loc_1102C` 在呼叫戰鬥主函式 `sub_39B6E` 之前，連續七次 `FreeMem`：

```
0xB08, 0x520, 0xA38, 0x520, 0xA98, 0x298, 0x718 bytes
```

政略與戰鬥的狀態是**分開配置**的，不共用緩衝。remake 不需要重現這個
記憶體管理，但它證實了兩個階段的狀態互不干涉——`internal/game` 可以
把政略與戰鬥切成兩組狀態，不必擔心原版有隱藏的共用欄位。

## 4. 隨機決策的分佈 — **confirmed**

`WAR.EXE` 有 **53 個 `Random` 呼叫**（外加開頭一次 `Randomize`），
散在 24 支函式裡。範圍參數直接暴露了機率結構：

| 範圍 | 次數 | 出現在 |
|---:|---:|---|
| `Random(10)` | 18 | 最主力——十分之一骰。`sub_3964E` 一支就佔 6 次 |
| `Random(5)` | 6 | `sub_36D74`(3)、`sub_1AA28`、`sub_1FC1C`、`sub_35B19` |
| `Random(2)` | 6 | `sub_11C04`(3) 等 |
| `Random(500)` | 4 | `sub_21D1D` |
| `Random(349)` | 4 | `PROGRAM`(3)、`sub_3562B` |
| `Random(3)` | 2 | `sub_1A729`、`sub_1AA28` |
| `Random(6)` | 2 | `sub_24535`、`sub_35E89` |
| `Random(278)` | 1 | `PROGRAM` |
| `Random(700)` | 1 | `sub_19918` |
| `Random(60000)` | 1 | `sub_303CD` |
| 其他（8、9、15、20）| 4 | |

`Random(10)` 佔三分之一——**原版的隨機判斷主要是十分之一骰**，
remake 要對齊機率就從這個粒度開始。

⚠️ `Random(278)` 接近 `MAN115` 的 274 位將領但**不相等**，
不要當成「隨機選一位將領」。

## 5. 勢力覆滅時清空該省資源 — **confirmed（程式碼）／假說（語意）**

`sub_3964E`（戰鬥結束後由 `sub_39B6E+6F4` 呼叫，`docs/re/04`）裡有**三段
完全相同**的程式碼，各自跑一個遍歷全省的迴圈：

```
for 省 = 1 to word_7001E:
        di = 37 * 省
        if [di - 6221h] != word_70026:  continue     ; 讀 記錄[省] 的 +20
        di = 37 * 省 + 9DCBh
        [di + 0] = Random(10)
        [di + 2] = Random(10)
```

### 每個常數都對上 SPEC-03

| 組語 | 意義 | 來源 |
|---|---|---|
| `mul 25h` | ×37 = 省份記錄大小 | `docs/spec/03` §1 |
| `[di - 6221h]` | 基址 `0x9DDF` + 省×37 | |
| `di + 9DCBh` | 基址 `0x9DCB` + 省×37 | |
| 兩個基址相差 **20** | `+20` 正是**司令**欄位 | `docs/spec/03` §2 |
| 寫入 `+0`、`+2` | **黃金**與**糧食** | 同上 |

**兩條獨立的線索交叉印證**：戰鬥 gate（§2）讀的也是 `[di-6221h]`，
所以 `sub_5C7FE` 收到的確實是司令 ID——§2 裡標為「強證據」的那一點
**升級為 confirmed**。

### 語意：某個勢力覆滅，它的省被洗掉 — **假說**

程式行為是確定的：**篩出所有司令等於 `word_70026` 的省，
把黃金與糧食重設為 0–9 的隨機值**。

把資源設成個位數等於清空，所以最合理的解釋是「某個勢力被消滅時，
它名下所有省份的資源歸零」。`word_70026` 就是那個勢力的領袖 ID。

三段相同的程式碼很可能對應三種角色（攻方／守方／第三方），
但**沒有驗證**。`byte_70056`、`byte_6BCD1` 與 `byte_6C952` 是進入這段的前置條件，
語意也未解。

### 對 remake 的意義

這是目前唯一一條**讀到程式碼**的結算規則。它同時說明：
省份資料表在戰鬥結算時**會被就地改寫**，政略與戰鬥不是完全隔離的
（雖然記憶體緩衝是分開配置的，見 §3）。

## 6. 還完全沒解的部分 — **未知**

這一份目前只涵蓋「哪個省會進戰鬥」，AI 真正的決策全都還沒挖：

| 問題 | 下一步從哪挖 |
|---|---|
| 電腦選哪個政略指令（15 選 1）| 找政略指令分派器，看電腦走哪條路 |
| 出兵目標怎麼選 | 攻打候選 = 鄰省 − 己方省（SPEC-01 §2 已驗），但**排序規則**未知 |
| 派將怎麼挑 | 將領記錄 33 B 只解出三個能力值與兵力（SPEC-02），選將公式未知 |
| 兵力配置比例 | 未知 |
| 撤退／求和門檻 | 未知 |
| 電腦怎麼用這 53 個亂數 | 呼叫點已盤（§4），但每一處的語意還沒逐支追 |
| 難度參數 | 不確定原版有沒有難度設定 |

### 建議的挖掘順序

1. ~~盤 `Random` 的所有呼叫點~~ **已完成**，見 §4。
2. **從 `Random` 次數最多的函式往下追**：`sub_3964E`(6，已解一部分，見 §5)、
   `sub_19D6A`(6)、`sub_21D1D`(5)、`PROGRAM`(5)。次數多代表決策密集。
3. 找政略指令的分派器（15 個分支的 jump table 或連續 cmp）。
4. 從分派器往回找「電腦走的那一條」——玩家與電腦多半共用同一批動作函式，
   差別在誰來決定參數。

---

## 7. 給 remake 的設計提醒

- **決策粒度在省**（§1）。要做強化 AI 可以另外加一層全局規劃，
  但那必須標記為 remake 差異，不能混進「還原原版」的路徑。
- 條件判斷用的是**線性搜尋十大勢力表**，不是位元遮罩——
  代表勢力數量在原版是硬上限 10。remake 若要支援更多勢力，
  這是第一個要改的地方，也要標為差異。
