# 機制：電腦 AI 的判斷邏輯

依 `CLAUDE.md` §6.5，這是機制文件裡優先度最高的一份——
remake 之後要調難度、改進電腦對手、或做強化 AI，全靠這裡。

推論等級的定義見 `00-index.md`。

---

## 1. 勢力輪替：主迴圈逐省處理 — **confirmed**

`WAR.EXE` 的 `PROGRAM`（`docs/re/06`）是一個以 `byte_6FE89` 為迴圈變數的大迴圈，
**變數代表當前處理到第幾個省**。每一輪對該省跑一串 gate，決定要走哪條路。

也就是說，遊戲的推進單位是**省**，不是「勢力」——電腦不是「每個勢力想一次」，
而是「每個省被輪到時判斷一次」。這對 remake 的 AI 設計是關鍵前提：
原版的決策粒度在省，改成勢力層級的全局規劃會是**行為改動，不是還原**。

驗證位址：`PROGRAM` 的 `loc_10C18`（迴圈頭）、`loc_11002`（戰鬥 gate）。

## 2. 「這個省要不要進戰鬥」的三個條件 — **confirmed**

```asm
loc_11002:
        mov     al, byte_6FE89      ; 當前省
        mov     dx, 25h             ; ×37 = 省份記錄大小（SPEC-03）
        mul     dx
        mov     di, ax
        push    word ptr [di-6221h] ; 省份記錄裡的一個 word
        call    sub_5C7FE
        or      al, al
        jnz     loc_1102C           ; 1. 成立 → 進戰鬥
        cmp     byte_7003A, 0
        jnz     loc_1102C           ; 2. 成立 → 進戰鬥
        cmp     byte_7003B, 0
        jnz     loc_1102C           ; 3. 成立 → 進戰鬥
        jmp     loc_11143           ; 都不成立 → 這個省跳過
```

三個條件是 **OR**，任一成立就打。

### 條件 1：司令是不是十大勢力之一（`sub_5C7FE`）

```
sub_5C7FE(arg: word) -> boolean
    if byte_7003A != 0:  return false
    if arg == 0:         return false
    for i = 1 to 10:
        if arg == 表[i]: return true
    return false
```

**在一個 10 元素的 word 表裡線性搜尋**。第一期正好有 10 個勢力
（張作霖、孫傳芳、吳佩孚、蔣中正、劉湘、唐繼堯、袁祖銘、趙恆惕、閰錫山、馮玉祥，
見 `docs/spec/03` §3），而傳進去的 word 來自省份記錄，司令欄位存的正是將領 ID。

- 迴圈從 **1** 數到 10，不是 0——與將領 ID 是 1-based 一致（SPEC-03 §3）。
- `arg == 0` 直接回 false，對應「無主的省」。

**傳入的是司令 ID 已經是 confirmed**——§5 從另一條路（`sub_3964E` 用同一個
基址讀 `+20`、寫 `+0`／`+2`）交叉印證了這一點。

⚠️ 但**十大勢力表本身的內容是執行期填的，靜態看不到**。
「表裡裝的就是那十位領袖」仍是從「10 這個數字 + 傳入的是司令 ID」推的
**強證據**，要完全確認得動態 dump 或找到填表的程式碼。

### 條件 3：`byte_7003B` 是「觀戰」開關 — **confirmed（程式碼）／強證據（語意）**

`byte_7003B` 全 `WAR.EXE` **只有一個寫入點**：`sub_1BF58`，而那是個 toggle：

```asm
cmp     byte_7003B, 0
mov     al, 0
jnz     short loc_1C04B
inc     ax                      ; 0 → 1
loc_1C04B:
mov     byte_7003B, al
... 畫一個框 ...
cmp     byte_7003B, 0
jz      short loc_1C08B
OUTTEXTXY(..., "ON")            ; 開
jmp     short loc_1C09D
loc_1C08B:
OUTTEXTXY(..., "OFF")           ; 關
```

**輸出 ON/OFF 字串的設定開關**。`sub_1BF58` 由 `sub_1C38C` 呼叫，
是設定選單的一項。

配合 `2.15` 詞條 147「**觀戰**」，方向相反的謎就解開了：

| 位置 | 開關打開時 | 讀起來 |
|---|---|---|
| `sub_5C7FE` 開頭 | return false | 「這個省不算我的勢力」|
| 主迴圈 gate | 進戰鬥 | 「但還是要進去看」|

**觀戰模式：不是自己的省也進戰鬥畫面**。兩處行為完全自洽。

⚠️ 語意標**強證據**而非 confirmed——ON/OFF 開關與 toggle 行為是讀到的，
「這個開關叫觀戰」是從詞表與兩處用法推的，沒有直接讀到標籤字模。

### 條件 2：`byte_7003A` — **未知**

只在 `PROGRAM` 初始化時設 0，**全檔沒有其他寫入點**。
所以在正常流程下它恆為 0，這個條件永遠不成立——可能是開發期的 debug 旗標。

`sub_5C7FE` 開頭也檢查它（非 0 直接 return false），與 `7003B` 同樣的用法。


## 3v. ✅ 「被包圍就突圍」`sub_5A9F6` / `sub_170C0` — **confirmed**

決策鏈 A 的**步驟 4 與步驟 6** 都用它：

```
步驟 6：sub_5A9F6(當前省) 為真 → sub_17236 → sub_174C9（出兵）
步驟 4：sub_170C0 在鄰省表裡找第一個滿足它的省
```

### `sub_5A9F6`：每一個有效鄰省都是敵方的

```
total = 有效鄰省數（非 0、非 255）
enemy = sub_5A907(該省司令, …, 該省) 收集到的敵對鄰省數
回 total == enemy
```

**被敵人完全包圍 → 出兵突圍。** 這是很直觀的求生行為。

### [雷] `sub_5A907` 的「敵對」不含無主省

```
鄰省編號 != 0 且 != 255       ← 有效
該省司令 != 0                  ← **無主省不算敵人**
該省司令 != 我方勢力           ← 不是自己人
```

**這與攻打候選的規則正好相反**——攻打要的是「司令不同**且非無主**」
（`20-military.md` §1b），而這裡把無主省從敵人裡排除。
所以**一個被無主省環繞的省不算被包圍**，電腦不會為它啟動突圍。

⚠️ 沒有任何有效鄰省時（四面環海），`0 == 0` 成立，**原版會回 true**。
一個孤島省會被判成「被包圍」。看起來像邊界情況沒被想到，
但那是原版行為，`internal/game/aiencircled.go` 照抄不改。

實作在 `internal/game/aiencircled.go`。

## 3w. ✅ 優勢比門檻 `sub_16F89` — **confirmed**

**決策鏈 A 的步驟 1 與步驟 3 都用它**。步驟 1 拿它決定
「出兵（`sub_174C9`）還是只調動（`sub_14F9A`）」——
所以這是「電腦要不要打」最直接的一道判斷。

```
mine   = ProvinceStrength(當前省)     ; sub_5B983
theirs = ProvinceStrength(目標省)
回 theirs × 倍數 ≤ mine

倍數：高難度 4、低難度 3
```

**電腦要有 3–4 倍的戰力優勢才出手。**

### ⚠️ 高難度反而更保守

倍數 4 > 3，讀起來反直覺，但與補給門檻（§3x：高難度要求更多存糧）
**方向一致**。合起來的行為是：**高難度的電腦更謹慎，只在絕對優勢時才動手**
——它不亂送兵，實際上更難對付。

這是 `byte_6FFCA` bit 0 的**第四個用途**。四個用途整理：

| 位元 | 用途 | 出處 |
|---|---|---|
| bit 0 | 救援調動用模式 7 而非 5 | `docs/re/11` §6 |
| bit 0 | 慰勞的體力／士氣門檻（80/70 vs 60/50）| §3y |
| bit 0 | 養兵成本除數（50 vs 70）| §3x |
| bit 0 | **出兵的優勢倍數（4 vs 3）** | 本節 |

### `sub_5B983` 就是 `ProvinceStrength`

掃全部將領，取 `+4`（所屬省）符合且 `+16` bit 0 為 1 的，
累加 `sub_5A0B9` 的攻擊力——與 `internal/game/strength.go` 的
`ProvinceStrength` 完全相同。

**「AI 的評估函式就是攻擊力公式」的第三個獨立例子**
（前兩個是調動 §6e、談判停火 `50-diplomacy.md` §1z）。

實作在 `internal/game/aiadvantage.go`。

## 3x. ✅ 補給門檻 `sub_16B44` — **confirmed**（六步裡出現四次）

**決策鏈 A 的六個步驟裡，步驟 1、3、5、6 都先呼叫它**（`docs/re/28` §2）——
因為每個「要花資源的步驟」都先問一句「這個省的補給夠不夠」。
解開它等於一次補上四步的前提。

```
簡單模式（byte_6FFCA & 4 未設）：
    黃金 ≥ 1,000 且 糧食 ≥ 10,000

進階模式（bit 2 已設）：
    需求 = 兵力總和 ÷ (bit 0 ? 50 : 70)
    需求 ≤ 黃金 且（需求 × 10 ≤ 糧食 或 糧食 ≥ 25,000）   → 充足
    或 黃金 ≥ 4,000 且 糧食 ≥ 25,000                       → 充足

兩套都要再過最後一關：
    彈藥 ≥ 15,000 且 燃料 ≥ 10,000
```

### 三個讀得出來的設計

1. **彈藥與燃料是硬門檻。** 前面的錢糧判斷再寬鬆，這兩個不夠一律回 false。
   錢再多也打不了沒有彈藥的仗。
2. **難度影響「養兵成本」的估算**：高難度用 ÷50、低難度用 ÷70，
   除數越小需求越大——**高難度的電腦要求更多存糧才敢動**。
   這是 `byte_6FFCA` bit 0 的**第三個用途**。
3. **`byte_6FFCA` bit 2 不只是「啟用最後三步」**（`70-ai.md` §6d 原本的說法），
   它同時切換補給判定走簡單還是進階公式。

⚠️ 兵力總和來自狀態結構的 `ss:[di-236h]`（32-bit）。**那一格的語意是假說**
——形狀與用法都像兵力總和（步驟 5 也拿它跟 63,392 比），
但沒有直接證據，`internal/game/aisupply.go` 由呼叫端傳入。

實作在 `internal/game/aisupply.go`。

## 3y. ✅ 決策鏈 A 第一步：要不要慰勞軍民 — **confirmed**

`sub_16E77`（148 行）。**這是第一條解出來的「電腦為什麼選這個指令」**——
`docs/re/28` 只解出六個步驟的骨架，每一步的判斷函式都還是黑盒，這是第一個打開的。

```
for 該省的每個將領 g:
    g.+4（所屬省）  != 目標省        → 跳過
    g.+16           != 1             → 跳過   ← 完全等於 1，不是 bit test
    g.+14（效忠）   != 省.司令(+20)  → 跳過
    Round(g.兵力 ÷ sub_349C1(g)) < 10000 → 跳過
    若 體力 < 門檻 或 士氣 < 門檻    → **回 true（慰勞）**
回 false
```

### 兩檔難度門檻（`byte_6FFCA & 1`）

| 難度 | 體力 | 士氣 |
|---|---:|---:|
| 高（bit 0 = 1）| < 80 | < 70 |
| 低 | < 60 | < 50 |

士氣上限是 **80**（`MoraleMax`），所以高難度的門檻 70 相當接近滿值——
**電腦在高難度下會更勤於維持部隊狀態**，低難度則要掉到很低才理。
這是 `byte_6FFCA` bit 0 的**第二個用途**（第一個見 `docs/re/11` §6）。

### 兵力門檻就是「半滿」

`sub_349C1` 回的是 **1 / 人力權重**（`docs/re/10` §3），所以
`兵力 ÷ (1/權重) ≥ 10000` 等價於 **`兵力 × 權重 ≥ 10000`**：

| 權重 | 滿員 | 門檻 |
|---:|---:|---:|
| 1 | 20,000 | 10,000 |
| 10 | 2,000 | 1,000 |
| 100 | 200 | 100 |

全部正好是滿員的一半。**電腦不慰勞殘兵**——兵力掉太多的部隊它走別的步驟
（撤回後方之類），不把指令數浪費在上面。

這是「兵力門檻一律用 `兵力 × 人力權重` 表達」第三個獨立出現的例子
（前兩個在 `docs/re/10`）。

實作在 `internal/game/aicomfort.go`。

## 3u. ✅ 軟柿子判定 `sub_17019` / `sub_306CF` — **confirmed**

**它問的是敵方目標省，不是自己的省。** 兩個呼叫端傳的都是目標：

| 呼叫端 | 傳誰 |
|---|---|
| 步驟 3（`sub_17ADA+314`）| 掃到的每一個**敵對鄰省** |
| 出兵準備（`sub_174C9+CC`）| 已經挑好的**目標省**（`ss:[bp_17ADA-2]`）|

所以語意是：**那個省缺糧、而且四面都是它的敵人 → 孤立無援，打它划算。**

與 `sub_16F89` 是同一類判斷的兩種角度，步驟 3 **二選一成立就收進候選**：

```
sub_16F89   我方壓倒它（3–4 倍優勢）
sub_17019   它自己撐不住
```

⚠️ `sub_5A9F6`（被包圍）在這裡與步驟 6 用的是**同一支函式、相反的意思**：
步驟 6 問「**我的**省被包圍了嗎」→ 突圍；這裡問「**它的**省被包圍了嗎」→ 進攻。
判斷用的是該省自己的司令當基準，所以換個對象問就換個意思。

### `sub_17019`：缺糧 **且** 被包圍

```
force = sub_306CF(省)                    ; 該省的兵力總和（32-bit）
若 黃金 < force/100  → 進包圍檢查
否則 若 糧食 < force/10 → 進包圍檢查
否則 → 回 false

包圍檢查： sub_5A9F6(省) 為真 → 回 true，否則 false
```

前半是「或」（黃金與糧食任一不足），前後半之間是「且」。
所以完整語意是 **「補給撐不住，而且四面都是敵人」**——走投無路。

### 除數 100 / 10：同一套「黃金:糧食 = 1:10」比例

`sub_16B44` 的進階模式算的是 `need = 兵力 ÷ 50（或 70）`，
再拿 `need` 比黃金、`need × 10` 比糧食（§3x）。這裡是同一個 1:10 的比例，
只是除數換成 **100**——**除數更大 → 需求更小 → 這一關寬鬆一倍以上**。

兩支問的是不同的問題：

| 函式 | 除數 | 問題 |
|---|---:|---|
| `sub_16B44` | 50 / 70 | **我**有本錢行動嗎（要不要花指令數）|
| `sub_17019` | 100 | **它**快撐不住了嗎（值不值得打）|

⚠️ 兩支的**對象不同**——一個問自己的省，一個問目標省。

### `sub_306CF`：某省的兵力總和 — **confirmed**

篩選條件與 `sub_5A881`（將領數，§6i）**逐字相同**：

```
將領 +4  == 省編號
將領 +16 bit 0 == 1
將領 +14 == 該省的司令（省份 +20）
    → 累加 +17（兵力）成 32-bit
```

原版特地用 `add`/`adc` 湊成 long 回傳，代表它預期總和會超過 65,535——
三個滿員步兵師（20,000）就到了。

### ⚠️ `sub_306CF` 開頭有一段死碼

```
若 省份 +32 bit 6（交戰中）→ 回傳值 := 0
...
loc_3077C:  回傳值 := 累加結果        ← 無條件覆寫
```

那次清零**完全沒有效果**。所以**交戰中的省不會被特別處理**，
`internal/game/aidesperate.go` 照抄實際行為，不模擬那段死碼。

這是 `byte_6FFCA` 之外第二個「寫了但沒生效」的地方，
與 `docs/re/28` 記過的模式一致：判斷寫在前面、結果在後面被覆寫。

實作在 `internal/game/aidesperate.go`。

## 3r. ✅ 步驟 5：柿子挑軟的捏 `sub_16047` — **confirmed**

**決策鏈 A 的最後一支判斷函式**，解完之後這條鏈的十支判斷全部到齊。

### `sub_16047(狀態, mode, n, 候選[])` 是**就地排序**

排序鍵是 `sub_5B983(省)` = 該省可用將領的**戰力總和**（32-bit）——
與 §6h 排序調動目標、§3w 算優勢比用的是同一支。
**AI 的評估函式就是攻擊力公式**，這是第四個獨立的例子。

| mode | 方向 | 呼叫端 | 取誰 |
|---:|---|---|---|
| 1 | 升序 | 決策鏈 A 步驟 5（`sub_17ADA+4E2`）| **最弱的鄰省** |
| 2 | 降序 | `sub_1655C+45`（未解）| 最強的敵對鄰省 |

兩個呼叫端都只取排序後的**第一個**，所以實際語意是「挑最弱的／挑最強的」。

⚠️ 它**改動呼叫端的陣列**，不是回傳一個省。`docs/re/28` 的欄位掃描
把 `es:[di-1]` 記成「回傳值」，實際上那是寫回候選陣列本身。

⚠️ 原版是雙迴圈選擇排序、相等不交換。這種寫法**不是穩定排序**，
所以並列時第一名以外的排列與 `sort.SliceStable` 不同——
`internal/game` 照抄同樣的雙迴圈。

### 步驟 5 的完整語意

```
byte_6FFCA & 2                          ; bit 1，啟用這一步
[-234h] > 3
[-236h] ≥ F7A0h (63,392)                ; 疑似兵力總和（假說）
sub_5B7DC（有敵對鄰省）+ sub_16B44（補給夠）
掃 8 個鄰省，**跳過交戰中的**（+32 bit 6）→ 候選
sub_16047(mode 1) → 取第一個 = **戰力最弱的**
→ sub_174C9(狀態, 3)                     ; 出兵模式 3
```

門檻高（要 bit 1、要兵多、要補給），所以這是**兵多將廣時的擴張**，
而擴張的對象是**柿子挑軟的捏**——與步驟 1 的「要 3–4 倍優勢」
（§3w）方向一致，但這裡不比自己的戰力，只挑對方最弱的。

### 三種出兵模式

`sub_174C9` 的第二個參數目前看到三個值：

| 模式 | 來源 | 情境 |
|---:|---|---|
| 1 | 步驟 6 | 被包圍，突圍 |


## 5. 勢力覆滅時清空該省資源 — **confirmed（程式碼）／假說（語意）**

`sub_3964E`（戰鬥結束後由 `sub_39B6E+6F4` 呼叫，`docs/re/04`）裡有**三段
完全相同**的程式碼，各自跑一個遍歷全省的迴圈：

```
for 省 = 1 to word_7001E:
        di = 37 * 省
        if [di - 6221h] != word_70026:  continue     ; 讀 記錄[省] 的 +20
        di = 37 * 省 + 9DCBh
        [di + 0] = Random(10)
        [di + 2] = Random(10)
```

### 每個常數都對上 SPEC-03

| 組語 | 意義 | 來源 |
|---|---|---|
| `mul 25h` | ×37 = 省份記錄大小 | `docs/spec/03` §1 |
| `[di - 6221h]` | 基址 `0x9DDF` + 省×37 | |
| `di + 9DCBh` | 基址 `0x9DCB` + 省×37 | |
| 兩個基址相差 **20** | `+20` 正是**司令**欄位 | `docs/spec/03` §2 |
| 寫入 `+0`、`+2` | **黃金**與**糧食** | 同上 |

**兩條獨立的線索交叉印證**：戰鬥 gate（§2）讀的也是 `[di-6221h]`，
所以 `sub_5C7FE` 收到的確實是司令 ID——§2 裡標為「強證據」的那一點
**升級為 confirmed**。

### 語意：某個勢力覆滅，它的省被洗掉 — **假說**

程式行為是確定的：**篩出所有司令等於 `word_70026` 的省，
把黃金與糧食重設為 0–9 的隨機值**。

把資源設成個位數等於清空，所以最合理的解釋是「某個勢力被消滅時，
它名下所有省份的資源歸零」。`word_70026` 就是那個勢力的領袖 ID。

三段相同的程式碼很可能對應三種角色（攻方／守方／第三方），
但**沒有驗證**。`byte_70056`、`byte_6BCD1` 與 `byte_6C952` 是進入這段的前置條件，
語意也未解。

### 對 remake 的意義

這是目前唯一一條**讀到程式碼**的結算規則。它同時說明：
省份資料表在戰鬥結算時**會被就地改寫**，政略與戰鬥不是完全隔離的
（雖然記憶體緩衝是分開配置的，見 §3）。

## 6. 政略流程的兩條路徑 — **confirmed（結構）／未知（語意）**

`PROGRAM+446` → `sub_1ACCC` → `+255` → `sub_15F3C` 是政略階段的處理鏈。

`sub_15F3C` 開頭先清空 8 格暫存（8 = 鄰省表的大小），然後用
**`sub_5B7DC` 的回傳值分流**——那支回傳「第一個可攻打的鄰省」
（`20-military.md` §1b）：

| 分流 | 意義 | 流程 |
|---|---|---|
| 回 0 | **沒有可攻打的鄰省** | `sub_15018` → `sub_15667` → `sub_150FC(1)` → `sub_1527A` → `sub_15925(0)` → *`sub_15A9A`* |
| 回非 0 | **有可攻打的鄰省** | `sub_1541E` → `sub_150FC(2)` → `sub_15925(1)` → *`sub_15A9A`* → *`sub_15CE3`* |

斜體的兩步有額外條件：`byte_6FFCA & 4` 才執行。

### 三個結構特徵

1. **每一步之前都檢查 `[di-7]`**，非 0 就跳過後續——中途取消的旗標。
   使用者按 ESC 或條件不成立時，剩下的步驟全部略過。
2. `sub_150FC` 與 `sub_15925` **同一支函式用不同參數**（1/2、0/1），
   代表兩條路徑共用邏輯、只差模式。
3. `sub_15667`、`sub_150FC`、`sub_1541E` **三支都會遍歷鄰省表**，
   各自屬於不同的步驟。

### 這對 AI 的意義

**電腦的第一個判斷是「有沒有可攻打的鄰省」**，而不是「我想做什麼」。
決策從地理條件出發，這與 §1「決策粒度在省」是一致的設計。

### `sub_15925`：收集候選鄰省，門檻依模式而定 — **confirmed**

兩條路徑都會呼叫它，只差參數（路徑 A 傳 0、路徑 B 傳 1）：

```
門檻 = (arg == 0) ? 5 : 25
清空 8 格候選陣列
if 門檻 > [某個值]:  直接結束        ; 資源／數量不足
for j = 1 to 8:
    n = 記錄[省].鄰省[j]
    if n == 0 or n == 0xFF:        continue
    if !sub_1588C(n):              continue   ; 另一層過濾，內容未解
    if 記錄[n].+32 & 0x40:          continue   ; 位元旗標排除
    候選[++count] = n
```

**5 與 25 是兩個模式的門檻值**。門檻大於某個量就直接結束——
所以這一步是「資源夠不夠做這件事」的檢查，不夠就跳過。
那個被比較的量從呼叫者的 stack frame 取（Pascal 巢狀函式的 static link），
**是什麼還沒追**。

這一步同時揭露了省份記錄 `+32` 是位元旗標欄位（`docs/spec/03` §2b）——
`0x40` 設了的省會被排除在候選之外。

### `sub_1588C`：放行無主省與「自己人太少」的省 — **confirmed**（2026-08-01 訂正）

`sub_15925` 用它當第二層過濾。完整內容：

```
n_gen = sub_5A881(n)                          ; 該省效忠其司令的可用將領數

if 記錄[n].司令 == 0:                → **通過**   ; 無主省，可以去佔
if 記錄[n].司令 != [呼叫者的勢力]:    → 否決       ; **敵省**
                                              ; （到這裡的都是自己的省）
if sub_5B7DC(我方, n):                         ; n 是前線省
    if n_gen ≤ 15:                  → 通過       ; 人少就去補
    else:                           → 否決
else:                                          ; n 是後方省
    if n_gen ≤ 2:                   → 通過       ; 人很少才去補
    else:                           → 否決
```

⛔ 這一節原本寫的是「司令 == 0 → **否決**」，把 `cmp word ptr [di-6221h], 0 /
jz short loc_15912` 讀反了——`loc_15912` 設的是 `var_1 = 1`（**通過**），
不是否決。連帶把整支函式描述成「與攻打規則同一套判準」，
但它收的其實是**自己人的省與無主省，一個敵省都不收**。

⚠️ 前線省的上限 15 與 `sub_1527A` 的屯兵上限（`AIFrontlineGeneralCap`）
是同一個數字，後方省的 2 則更嚴——與 §6l「一以貫之的傾向：分散，不集中」
一致。`internal/game/ai.go` 的 `transferable` 實作**一直是對的**，
錯的只有這份文件的偽碼。

所以候選收集的過濾是**兩層疊加**：先 `sub_1588C` 的勢力＋人數判斷，
再 `+32 & 0x40` 的旗標排除（交戰中的不收）。

### `sub_15018`：清點某種將領，再決定分支 — **部分解**

路徑 A 的第一步。前段是一個計數迴圈：

```
count = 0
if byte_6FE88 == 1 and (byte_6FFCA & 4):
    for j = 1 to 24:
        id = 清單[j]                      ; ds:[j*2 - 534Ah]，24 格的 word 陣列
        if id == 0: continue
        if 將領[id].+0 & 1:  count++       ; 33 stride，基址 7A8Dh
```

後段用 `count` 分支：`count == 2` 時，依 `byte_6FFCA & 1` 走 7 或 5。

**24 格的 word 陣列**裝什麼未知（勢力有 10 個、省有 39 個，都對不上 24）。

#### [訂正] 這裡讀的是 `+16`，不是 `+0`

本節原本寫「讀 `將領[id].+0` 的 bit 0」，並據此推論「執行期結構與檔案
結構不同」。**那個偏移我算錯了。**

`sub_15018` 讀的是 `[di + 7A8Dh]`，其中 `di = 33 × id`。
執行期將領表的基址是 **`0x7A7D`**（`sub_54826` 有直接的 `add di, 7A7Dh`），
所以偏移是 `0x7A8D − 0x7A7D` = **16**。

檔案的 `+16` 本來就未解（`docs/spec/02` 只解出 `+0/+1/+2/+4/+17`），
檢查它的 bit 0 沒有任何矛盾。

**執行期與檔案佈局看起來是一致的**——`+4`（所屬省）被 96 支函式存取、
`+17`（兵力）119 次，都是核心欄位該有的熱度。原本的警示不成立，已刪除。

留下的教訓不是「結構會變」，而是**算偏移要拿基址驗**：
基址寫在別的函式裡，光看單一存取點會猜錯。

⚠️ 仍未解：`sub_1527A`／`sub_15A9A`／`sub_15CE3` 的內容，
`byte_6FFCA` 各個位元的意義，24 格陣列裝什麼。

## 6b. 尋路權重與真實成本是分開的 — **confirmed**

這是目前解出來**最具體的一條 AI 行為參數**，也是 remake 要調難度時
一定會用到的東西。

`sub_4FCCC` 建一張 196×196 的全對全成本矩陣（`dword_6A454` 指向的
38,416 bytes）。建之前它會**暫時改寫三種地形的成本**，建完再改回來：

| 地形 | 建矩陣時（尋路權重）| 改回來（真實移動成本）| 倍率 |
|---|---:|---:|---:|
| 河海(3) | **30** | 12 | 2.5× |
| 沙漠(7) | **100** | 4 | **25×** |
| 有鐵路 | **1** | 2 | 0.5× |

矩陣本身的規則：

```
M[i][j] = 0        若 i == j
        = 50h(80)  若相鄰且 j 上面有單位
        = byte_9E2[j]（該格成本）  若相鄰且可通行
        = 0FFh     否則
```

### 這代表什麼

**AI 尋路時看到的地圖與實際走起來的地圖不一樣。** 沙漠實際只要 4 點
機動力，但規劃路徑時算 100——25 倍的差距，等於 AI 幾乎不會規劃穿越沙漠
的路線，即使那是最短路。河海同理（2.5 倍），鐵路則被加倍偏好（0.5 倍）。

這不是 bug，是**故意的行為偏好**：讓電腦部隊看起來「像會沿鐵路調兵、
繞開沙漠」，而不是機械地走最短路。

### 對 remake 的意義

兩組成本要分開實作，不能合成一組。要調電腦對手的行為（`CLAUDE.md` §6.5
說的「未來優化」），**改尋路權重比改真實成本安全**——後者會改變遊戲規則，
前者只改變 AI 的偏好。

真實成本表（`sub_506B0` 的完整分組）見 `30-combat.md` 與 `docs/re/07` §7。

## 6c. 難度／勢力加成：`byte_6FFCA` 的 bit 4–6 — **confirmed**

**這是目前找到最直接的難度參數**，攻擊力公式的最後一段
（`sub_5A0B9`，`docs/re/08` §4e）：

```
if 效忠的勢力是十大勢力之一（sub_5C7FE）:
    d = byte_6FFCA & 0x70
    d == 0x10:                     戰力 ×2
    d == 0x20:                     戰力 ×1.5
    d == 0x40 且 效忠者 == 蔣中正:   戰力 ×1.5
else:
    效忠者 == 蔣中正 且 byte_6FE88 == 1:  戰力 ×1.5
```

三個位元組成一個**三選一的加成設定**，套在「十大勢力」的單位上。

### 為什麼這是難度旋鈕

- `0x10` 讓所有十大勢力的單位戰力**翻倍**——玩家若不是十大勢力之一，
  等於全世界都變強一倍
- `0x20` 是溫和版（×1.5）
- `0x40` 只加給**蔣中正**（將領 ID 1，`docs/spec/03` §3）

而 `else` 那條分支專門給「效忠蔣中正但蔣不算十大勢力」的情況——
公式裡總共有**兩處**為 ID 1 開的特例。這是設計者給主角勢力的偏袒，
不是資料驅動的一般規則。

### 對 remake 的意義

要調整難度，**改 `byte_6FFCA & 0x70` 這一組是最乾淨的入口**——
它不動任何基礎數值，只縮放最終戰力。與 §6b 的尋路權重是同一類旋鈕：
原版把「難度」與「規則」分開了，remake 應該保持這個分離。

⚠️ 誰寫 `byte_6FFCA`、玩家在哪裡選這個設定，**還沒追**。
它的 bit 0 與 bit 2 在政略流程也有人讀（CONTEXT worklist #6d），
那兩個位元與這裡的 bit 4–6 是不是同一組設定，未確認。

## 6d. 電腦選指令的優先序 — **confirmed（結構）**

`CLAUDE.md` §6.5 把「電腦選指令的優先序」列為必記的第一項。
`sub_15F3C` 就是那條鏈。

```
sub_15F3C(狀態):
    暫存[1..7] = 0
    if sub_5B7DC(當前省) != 0:            ; 有敵對的鄰省 → 前線省
        sub_1541E(狀態)
        if 還沒決定: sub_150FC(狀態, 2)
        if 還沒決定: sub_15925(狀態, 1)
        if 還沒決定 且 (byte_6FFCA & 4): sub_15A9A(狀態)
    else:                                 ; 沒有敵對鄰省 → 後方省
        if 還沒決定: sub_15018(狀態)
        if 還沒決定: sub_15667(狀態)
        if 還沒決定: sub_150FC(狀態, 1)
        if 還沒決定: sub_1527A(狀態)
        if 還沒決定: sub_15925(狀態, 0)
        if 還沒決定 且 (byte_6FFCA & 4): sub_15A9A(狀態)
    if 還沒決定 且 (byte_6FFCA & 4): sub_15CE3(狀態)
```

### 三個結構特徵

1. **`ss:[di-7]` 是「已經決定要下什麼指令」的旗標。** 每一步之前都檢查它
   還是不是 0——**一旦某一步做出決定，後面全部跳過**。
   所以這是一條**由上而下的優先序**，不是評分後挑最高分。
2. **前線省與後方省走不同的鏈**，而且**後方省的鏈比較長**
   （6 步 vs 4 步）。合理：後方要做內政與生產，前線只管打。
3. **`byte_6FFCA` 的 bit 2 啟用最後三個決策步驟**（`sub_15A9A` 兩處與
   `sub_15CE3`）。關掉的話電腦少三種行為。

### `sub_5B7DC(省)` = 第一個敵對的鄰省 — **confirmed**

```
我的司令 = 省份[省].+20
for k = 1..7:
    if 我的司令 == 0:                  return 0
    鄰省 = 省份[省].鄰省[k]
    if 鄰省 == 0 或 0FFh:              continue
    if 省份[鄰省].司令 == 0:            continue   ← 無主省不算敵對
    if 省份[鄰省].司令 == 我的司令:      continue   ← 自己人不算
    return 鄰省
```

三個偏移（`+20` 司令、`+22` 鄰省表、`0FFh` 哨兵）都對得上 `SPEC-03`。

**無主省不算敵對**——這與攻打候選的規則（`SPEC-01` §2）一致：
攻打要求「司令不同**且非無主**」。

### 已知的步驟

| 步驟 | 已知 |
|---|---|
| `sub_15018` | **救援快撐不住的前線省**（戰力 < 2,000），掃全 39 省 + 尋路取第一步。見 `docs/re/11` |
| `sub_150FC` | **一般調動 = 往無主省擴張**，見 §6e |
| `sub_15925` | **往富省集中**（不是攻打）：門檻 25／5，目標依黃金**降冪**挑**最富**的。見 `docs/re/12` §5 |
| `sub_1541E` | 前線省把缺員部隊撤到後方（§6h），模式 4 |
| `sub_15667` | 後方省往人少的地方分兵（§6j），模式 3 |
| `sub_1527A` | 增援前線（§6f），目標省將領 < 15 |
| `sub_15A9A` | 往補給充足的省調動（§6k）|
| `sub_15CE3` | **未讀**（302 行，也呼叫 `sub_5BF74` 與 `sub_5A907`）|

## 6e. 調動：`sub_150FC` → `sub_14F9A` — **confirmed**

政略指令 1 是「調動行動」（`docs/playtest/02` §5 實機確認）。
決策鏈裡的 `sub_150FC` 就是它，而且**前線省與後方省傳不同的模式**。

### 挑目標省：四道守門

```
for k = 1..7:
    鄰省 = 省份[當前省].鄰省[k]
    if 鄰省 == 0 或 0FFh:              continue   ; 填充／海洋境外
    if 省份[鄰省].司令(+20) != 0:       continue   ; ← 只往**無主**省
    if !sub_13F4E(將領, 鄰省):          continue   ; §6g 的守門
    if sub_1401E(將領, 鄰省) 且 模式 == 1:  → 選中它
    if !sub_36BC7(鄰省):                continue   ; 未讀
    if 模式 != 2:                       continue
    if 省份[鄰省].+32 & 40h:            continue   ; **正在打仗的省不調**
    → 選中它
```

`+20`（司令）、`+22`（鄰省表）、`+32` bit 6（正在打仗）三個偏移都對得上
`SPEC-03`。

### ⛔ 訂正：這一條原本寫反了

初版寫成「無主省不調」，依據是這一行：

```asm
cmp     word ptr [di-6221h], 0
jnz     short loc_15219
```

**`jnz` 跳的是 skip 標籤**，所以留下來的是 `== 0` 的省——只往**無主**省。
配上下面「調動成功後目標省的司令改成我方」，一般調動的整體語意是
**往無人的省份擴張**，不是在自己的省之間搬來搬去。

寫反的代價是實跑時兩個省每回合互相搬兵、局面永遠不變
（`docs/playtest/05` §2）。**單元測試全綠，是實跑抓到的。**

候選**不排序**：原版每次符合就覆蓋 `ss:[di-3]`，所以挑到的是
迴圈裡**最後一個**符合的鄰省，不是第一個。

### 調動類型由目標省的處境決定

```
if 模式 == 2:                        類型 = 4
elif sub_5B7DC(選中的省) != 0:        類型 = 1     ; 目標省有敵對鄰省
else:                                類型 = 0     ; 目標省是安全的後方
sub_14F9A(將領, 類型, 選中的省)
```

配上 §6d 的優先序鏈：

| 省的處境 | 呼叫 | 得到的類型 |
|---|---|---|
| **前線**（有敵對鄰省）| `sub_150FC(2)` | **4** |
| **後方**，目標是前線 | `sub_150FC(1)` | **1** |
| **後方**，目標也是後方 | `sub_150FC(1)` | **0** |

也就是**後方省會把部隊往前線調**（類型 1），前線省之間的調動走類型 4。

### 執行：目標省的司令換人 — **confirmed**

```
sub_14F9A(將領, 類型, 目標省):
    sub_34105(目標省)                       ; 重畫
    sub_1408F(將領, &結果, 類型, 目標省)     ; 實際搬動，未讀
    if 結果 != 0:
        省份[目標省].+20 = 狀態[-2]          ; ← 目標省的司令改成調過去的人
        狀態[-7] = 1                         ; ← 標記「已決定」，優先序鏈到此結束
        sub_34105(當前省)
        if byte_6FE83 != 0: sub_137AB(...)
```

`mov [di-6221h], cx`（`di = 37 × 目標省`）落在記錄 `+20`，正是司令欄位
（`SPEC-03` §2）。**調動的效果就是把某個將領派到鄰省當司令。**

`狀態[-7] = 1` 就是 §6d 那條優先序鏈檢查的旗標——兩邊對上了，
確認整條鏈的控制流沒有讀錯。

⚠️ `sub_1408F`（實際搬動兵力）、`sub_13F4E`、`sub_1401E`、`sub_36BC7`
（三道守門）**都還沒讀**。所以「什麼條件下電腦會調動」只解出骨架。

## 6f. 增援前線：`sub_1527A` — **confirmed**

決策鏈裡的 `sub_1527A` **也呼叫 `sub_14F9A`**，所以它也是調動
——但守門條件與 `sub_150FC` 完全不同：

```
for k = 1..7:
    鄰省 = 省份[當前省].鄰省[k]
    if 鄰省 == 0 或 0FFh:                    continue
    if 省份[鄰省].司令 != 我方的勢力:          continue   ← 只調到自己人的省
    if sub_5B7DC(鄰省) == 0:                 continue   ← 目標省必須是前線
    if !(sub_14761(...) & 1):                continue
    if 省份[鄰省].+32 & 40h:                 continue   ← 正在打仗的不去
    if sub_5A881(鄰省) >= 15:                continue   ← 屯兵上限
    （還有一道與所屬省有關的檢查，frame 跨得深，未完全展開）
    → 選中
```

### 三條與 `sub_150FC` 的差別

| | `sub_150FC`（一般調動）| `sub_1527A`（增援前線）|
|---|---|---|
| 目標省的歸屬 | 任何**有主**的省 | **必須是自己人** |
| 目標省的處境 | 不限 | **必須有敵對鄰省** |
| 屯兵上限 | 無 | **可用將領數 < 15** |

所以 `sub_1527A` 的語意很清楚：**後方的將領往自己人的前線省集中，
但一個前線省最多屯 15 個將領。**

### 15 是真的會生效的門檻

`sub_5A881(省)` 是「該省效忠其司令且可用的將領數」（`docs/re/07` §9）。
先前在戰鬥增援 `sub_534FF` 看到的同一個函式配的是 `>= 100`
——那條**實質恆真**（全遊戲才 274 位將領）。

這裡是 **15**，而河南在 `SAVE(1)` 就有 25 位將領——**這條會真的擋住**。

**這是目前解出來最具體的一條 AI 行為參數**：電腦不會把所有部隊
堆到同一個前線省。要調整電腦的集結傾向，改這個數字最直接。

## 6g. `sub_14761`：這個省有沒有滿員／缺員的將領 — **confirmed**

決策鏈上四支函式的守門條件都出自這裡。

```
旗標 = 0
for id = 1 .. word_6BC4A:                     ; 全部將領
    if !(單位[id].+16 & 1):        continue    ; 不可用
    if 單位[id].+4 != 省:          continue    ; 不在這個省
    if 省份[省].司令 == id:        continue    ; 司令本人不算
    滿員 = Round(sub_349C1(id) × 20000)
    if 單位[id].兵力 == 滿員:       旗標 |= 1   ; ← bit 0
    elif 單位[id].兵力 < Round(sub_349C1(id) × 10000):
                                   旗標 |= 2   ; ← bit 1
return 旗標
```

| 位元 | 意思 |
|---:|---|
| 0 | 這個省**有兵力剛好滿員**的將領 |
| 1 | 這個省**有兵力不到半員**的將領 |

### 誰用哪一個位元

| 決策 | 檢查 | 讀起來 |
|---|---|---|
| `sub_1527A` 增援前線 | **bit 0** | 有滿員的部隊才調出去 |
| `sub_1541E`／`sub_15667` | **bit 1** | 有缺員的部隊才做某件事 |

**bit 1 那兩支很可能是徵兵／整編**——詞表有「徵兵」「整編」
「重新整編」「整編兵力」（`2.15`），而「有部隊缺員」正是那兩個指令的
前提。⚠️ 兩支的內容（各 290／276 行）**還沒讀**，這是方向不是結論。

### 滿員 = 20000 ÷ 兵種權重 — 原版明確算的

`sub_349C1(id)` 回傳一個係數，乘 20000 就是該將領的滿員兵力：

| 兵種 | 人力權重（`sub_5190E`）| 20000 ÷ 權重 | 資料實測 |
|---:|---:|---:|---:|
| 1 步兵 | 1 | 20,000 | 20,000 ✓ |
| 4 砲兵 | 10 | 2,000 | 2,000 ✓ |
| 5 裝甲兵 | 100 | 200 | 200 ✓ |
| 6 騎兵 | 2 | 10,000 | 10,000 ✓ |

`docs/spec/02` §6 原本把「權重 × 滿員 = 20000」記成**觀察**
——現在知道那是**原版程式明確算出來的**，`sub_349C1` 就是 `1 ÷ 權重`。

### 第二個藏在 Real 裡的滿員數

```
0x8F, 0x0000, 0x1C40  →  20000    （攻擊力公式的分母，docs/re/08 §4a）
0x8E, 0x0000, 0x1C40  →  10000    ← 這裡
```

兩個常數只差 exponent 一階（143 vs 142），尾數完全相同。
`CLAUDE.md` §1.5 那四個滿員數裡，**20000 與 10000 都是字面常數**
（只是編碼成 48-bit Real），2000 與 200 則是除出來的。

### 對 remake 的意義

**電腦的行為是一條寫死的優先序，不是效用函式。** 要改難度或行為，
可以在鏈上插隊或換順序，而不必重寫評分——這與 §6b（尋路權重）、
§6c（戰力加成）一樣，原版把「行為」與「規則」分開了。

## 6h. `sub_1541E`：前線省把缺員的部隊撤到後方 — **confirmed（結構）**

決策鏈裡**前線省的第一步**（§6d 路徑 A）。它也呼叫 `sub_14F9A`，
所以也是調動——但方向與 §6e、§6f 都相反。

```
if !(sub_14761(當前省) & 2):        return    ; 省內沒有缺員的部隊 → 不做
if 狀態[-236h] / 狀態[-22Eh] < 10000: return  ; 一道比值門檻，見下

候選 = []
for k = 1..7:
    鄰省 = 鄰省表[k]
    跳過 0／0FFh
    if 省份[鄰省].司令 != 我方勢力:   continue   ; 只找自己人
    if sub_5B7DC(鄰省) != 0:         continue   ; **目標省必須是後方**
    if 省份[鄰省].+32 & 40h:         continue   ; 正在打仗的不去
    if !sub_13F4E(將領, 鄰省):       continue
    候選 += 鄰省

依 sub_5B983(省) **升序**排序候選
sub_14F9A(將領, 4, 候選[0])          ; 挑戰力總和**最小**的那個
```

### 三種調動的方向完全不同

| 決策 | 在哪條鏈 | 目標省 | 前提 |
|---|---|---|---|
| `sub_1541E` §6h | 前線 | 自己人的**後方**省 | 有**缺員**的部隊（bit 1）|
| `sub_150FC` §6e | 兩條都有 | 任何**有主**的省 | — |
| `sub_1527A` §6f | 後方 | 自己人的**前線**省 | 有**滿員**的部隊（bit 0），且該省將領 < 15 |

讀起來是一組完整的輪調：**滿員的往前線送，缺員的撤回後方**。

### 排序鍵 `sub_5B983(省)` = 該省可用將領的戰力總和 — **confirmed**

```
總和 = 0
for id = 1 .. 將領總數:
    if 單位[id].+4 != 省:      continue    ; 不在這個省
    if !(單位[id].+16 & 1):    continue    ; 不可用
    總和 += sub_5A0B9(id)                   ; ← 攻擊力公式
return 總和                                 ; 32-bit
```

**AI 用的評估函式就是攻擊力公式 `sub_5A0B9`**（`docs/re/08` §4）。
這對 remake 很重要：規則層的 `game.Strength()` 不只算戰鬥，
**同時是電腦評估局勢的工具**——兩邊必須用同一份實作，
否則 AI 的判斷會與實際戰果脫節。

排序是**升序**（`i > j` 才交換），所以挑的是**戰力總和最小**的後方省。
讀起來像「把缺員的部隊補到最弱的後方」，但那是解讀不是證據。

### 那道 10000 的門檻：平均兵力 ≥ 半個滿員步兵師 — **confirmed**

`狀態[-236h]`（32-bit）÷ `狀態[-22Eh]` 必須 ≥ `2710h` = 10,000。

- 分母 = 當前省的將領數（`docs/re/10` §1）
- 分子 = 該省可用將領的兵力總和——`sub_13D23` 直接寫
  `狀態[-236h] = sub_306CF(當前省)`（`docs/re/13` §3）

所以這道門檻是**平均每個將領兵力 ≥ 10,000**（半個滿員步兵師）。

## 6i. 決策鏈的全貌：六個步驟都是調動，差在挑目標的條件 — **confirmed**

把 §6d 那條鏈的每一步都追過之後，浮現一個整體認識：

> **政略階段電腦做的事，就是「調動」一種。**
> 決策鏈的六個步驟**全部**呼叫 `sub_14F9A`。差別全在**挑哪個省當目標**。

⛔ 這裡原本寫「五個調動、一個攻打（`sub_15925`）」。`sub_15925` 的

**一個敵省都不收**——見 `docs/re/12`。

**電腦怎麼發動戰爭，目前是未解的。**

| 步驟 | 鏈 | 前提 | 目標省的條件 | 排序／挑選 |
|---|---|---|---|---|
| `sub_1541E` §6h | 前線 | 有缺員部隊 + 一道 10000 門檻 | 自己人的**後方**省，未交戰 | 戰力總和**最小** |
| `sub_150FC` §6e | 兩條 | — | 任何**有主**的省；模式 2 跳過交戰中的 | 掃到就選 |
| `sub_15667` §6j | 後方 | 有缺員部隊 + **將領數 ≥ 3** | **後方**省，未交戰，**將領數比自己少** | 戰力總和**最小** |
| `sub_1527A` §6f | 後方 | 有滿員部隊 | 自己人的**前線**省，未交戰，**將領數 < 15** | 掃到就選 |

### 一以貫之的傾向：分散，不集中

三處獨立的上限都在防止兵力堆在一個省：

- `sub_1527A`：前線省的將領數 **≥ 15 就不再增援**
- `sub_15667`：只往**將領數比自己少**的省分
- `sub_1541E`／`sub_15667`：排序挑**戰力總和最小**的省

**這是原版 AI 的核心行為特徵。** 要讓電腦更會集中兵力（更難打），
改這三處比改任何數值都直接。

## 6k. `sub_15A9A`：往補給充足的省調動 — **confirmed（門檻）**

## 6l. 規則層實作與已知差異

```
前線省 17 個、後方省 12 個
```

### 守門補上之後的分佈（`docs/re` 的三道守門，§6m）

```
補守門前：一般調動 18、撤回後方 6、分兵 5、攻打 **0**
補守門後：攻打 **9**、撤回後方 6、分兵 5、一般調動 2、增援前線 1、無動作 6
```

**一般調動從 18 降到 2，攻打從 0 升到 9。**

只會表現成「電腦不打仗」。與評分式的 AI 不同——那種漏一個權重
只是分數偏掉，還看得出來。

`internal/game/ai_test.go` 的 `TestGatesKeepAttackReachable` 就是盯這件事的：
攻打次數變 0 就失敗。

## 6m. 三道守門 — **confirmed（內容）／未定（語意）**

§6l 標為最高優先的三道守門。讀完之後 `AIWorld.Decide` 的「攻打 0 次」
才有辦法修。

### `sub_1401E(狀態, 目標省)` = 目標省比當前省窮 — **confirmed**

```asm
cmp 省份[目標省].+0（黃金）, 省份[當前省].+0 ; >= 就回 0
cmp 省份[目標省].+2（糧食）, 省份[當前省].+2 ; >= 就回 0
回 1
```

兩個偏移（`-6235h` = 記錄 `+0`、`-6233h` = `+2`）對上 `SPEC-03` §2。

**要回 1，目標省的黃金與糧食都必須比當前省少。**
`sub_150FC` 在模式 1（後方省的一般調動）時用它——所以**後方省優先把部隊
調到比自己窮的鄰省**。

⚠️ 與 §6k 的 `sub_15A9A`（往資源**充足**的省調動）方向相反。
兩者在鏈上的位置不同（`sub_150FC` 早、`sub_15A9A` 晚），
但為什麼要有兩種相反的傾向，**未解**。

### `sub_13F4E(狀態, 省)` = 掃鄰省找符合條件的 — **confirmed（結構）**

```
for k = 1..7:
    鄰省 = 省份[省].鄰省[k]
    跳過 0／0FFh
    if 單位[鄰省].+14 != 狀態[-2]:      continue
    if 狀態[-22Eh] == 1 且 鄰省 == 當前省:  ...
    if 狀態[-22Eh] < 2:                 continue
    found = 1

```

### ⚠️ `sub_13F4E` 裡有一個疑似原版 bug — **強證據**

那句 `單位[鄰省].+14` 拆開來是：

```asm
mov al, [di-6220h]      ; 鄰省編號（省份記錄 +22 的鄰省表）
mov [bp+var_3], al
mov al, [bp+var_3]
mov dx, 21h             ; 33 = 將領記錄大小
mul dx
mov di, ax
mov ax, [di+7A8Bh]      ; 將領表第 (鄰省編號) 筆的 +14（效忠勢力）
cmp ax, ss:[di-2]       ; 與我方勢力比
```

**用省編號當將領 ID。** 對照同樣做「這個鄰省是不是自己人」的
`sub_5B7DC`（§6d），正確的寫法是：

```asm
mov dx, 25h             ; 37 = 省份記錄大小
mul dx
mov ax, [di-6221h]      ; 省份記錄 +20（司令）
```

**兩個常數同時不同**（`21h`↔`25h`、將領表↔省份表），而型別剛好相容
（兩邊都是「勢力領袖 ID」的 u16），所以編譯器不會抱怨、執行也不會崩
——只是讀到不相干的將領。這是複製貼上改錯基址的典型形狀。

`SPEC-03` 已用 39 省的資料驗過 `+22` 確實是鄰省表（與 `WARPOS` 幾何鄰接
36/39 一致），所以「`var_3` 是省編號」沒有解讀空間。

#### 處理原則：照抄，並標記

`CLAUDE.md` §1 的定位是**還原**：「核心規則一律對齊原版」、
「不得默默改動遊戲規則」。**bug 也是原版行為的一部分**——
1992 年的玩家玩到的就是這個版本。

所以 remake 照抄這個索引，並在程式碼與文件標清楚它是什麼。
「修好它」會讓電腦的行為與原版不同，那是 remake 差異，
要由使用者決定，不是我們順手改掉。

⚠️ 標為**強證據**不是 confirmed：無法排除「前 39 個將領有特殊意義」
這種設計意圖，只是找不到任何支持它的線索。

### `狀態[-22Eh]` = 當前省的將領清單長度 — **confirmed**

同一格在四支函式裡被檢查，門檻各不相同：

| 函式 | 門檻 | 讀成「將領數」 |
|---|---|---|
| `sub_13F4E` | `== 1` 走特例、`< 2` 就跳過 | 只剩一個將領時特殊處理 |
| `sub_15667` | `>= 3` | 至少三個才分兵 |
| `sub_15A9A` | `>= 4` | 至少四個才往補給省調 |
| `sub_1541E` | 當分母（`x / y >= 10000`）| 平均兵力 ≥ 10,000 |

`sub_1408F` 把同一格當 **Pascal 陣列的長度欄**用：`arr[0]` 是元素數，
`arr[1..n]` 是將領編號，取出來立刻餵給 `sub_349C1`（兵種權重）
與 `×33 + 0x7A7D`（將領記錄定址）。**只可能是將領編號**
（`docs/re/10` §1）。

因此 §6h 那道沒解的門檻也解了：`狀態[-236h] ÷ 將領數 ≥ 10,000`
= **平均每個將領兵力 ≥ 半個滿員步兵師**。分子 `-236h` 仍待驗。

> `CLAUDE.md` §1.5 記的社群說法「每個省份有命令數上限」
> **回到未證實**——這一格不是它的證據，不要記回去。

### `sub_36BC7` 的完整語意

另兩條分支讀完了：

```
我的司令 = 省份[目標省].+20
for i = 1..5:
    候選 = 特殊省清單[i]
    if 候選 == 目標省:                              → 回 1
    if sub_5B76E(候選, 目標省):                      ; 兩者相鄰
        if 省份[候選].司令 == 我的司令:               → 回 1
    else:
        sub_5BF74(0, 我的司令, 11, 候選, 目標省)      ; 找路徑
        if byte_70013 > 1:                          → 回 1
回 0
```

也就是：**目標省必須與那五個特殊省之一有關聯**——是它本身、
與它相鄰且同勢力、或有一條路徑通到它。

一般調動（`sub_150FC` 模式 2）用這道守門，所以**電腦只往「通向那五個省
的方向」調兵**。這強化了「那五個省是戰略目標」的解讀，
但**是什麼樣的目標仍不猜**。

#### `sub_5B76E(a, b)` = a 是不是 b 的鄰省 — **confirmed**

```
if b 不在 1..39（27h）或 a 不在 1..39:  回 0
for k = 1..7:  if 省份[b].鄰省[k] == a:  回 1
回 0
```

`27h` = 39 正是省份數，而鄰省表只掃 7 格——與其他地方一致。

#### `sub_5BF74` 是省份層的路徑搜尋 — **強證據**

```asm
mov ax, 5F1h
call @GetMem$q4Word     ; 動態配置 1,521 bytes
```

**`5F1h` = 1,521 = 39 × 39。** 一張全省對全省的矩陣。

配上 stack 上的 `var_9F`（39+ bytes 的旗標陣列）與 `var_50`
（word 陣列，看起來是距離），加上迴圈裡呼叫 `sub_5BEFA` 取下一個節點
——這是**廣度優先或 Dijkstra 的形狀**。

`arg_4` 選權重：`10` 走 `sub_5BA56`、`11` 走 `sub_5BD7B`。
`sub_36BC7` 傳的是 **11**。結果寫進 `byte_70013`。

這與 `docs/re/07` §7 那張 196×196 的**戰場層**成本矩陣是同一個手法，
只是換到省份層。⚠️ 兩支權重函式與 `sub_5BEFA` 都**未讀**。
