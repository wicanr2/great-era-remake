# 機制：電腦 AI 的判斷邏輯

依 `CLAUDE.md` §6.5，這是機制文件裡優先度最高的一份——
remake 之後要調難度、改進電腦對手、或做強化 AI，全靠這裡。

推論等級的定義見 `00-index.md`。

---

## 1. 勢力輪替：主迴圈逐省處理 — **confirmed**

`WAR.EXE` 的 `PROGRAM`（`docs/re/06`）是一個以 `byte_6FE89` 為迴圈變數的大迴圈，
**變數代表當前處理到第幾個省**。每一輪對該省跑一串 gate，決定要走哪條路。

也就是說，遊戲的推進單位是**省**，不是「勢力」——電腦不是「每個勢力想一次」，
而是「每個省被輪到時判斷一次」。這對 remake 的 AI 設計是關鍵前提：
原版的決策粒度在省，改成勢力層級的全局規劃會是**行為改動，不是還原**。

驗證位址：`PROGRAM` 的 `loc_10C18`（迴圈頭）、`loc_11002`（戰鬥 gate）。

## 2. 「這個省要不要進戰鬥」的三個條件 — **confirmed**

```asm
loc_11002:
        mov     al, byte_6FE89      ; 當前省
        mov     dx, 25h             ; ×37 = 省份記錄大小（SPEC-03）
        mul     dx
        mov     di, ax
        push    word ptr [di-6221h] ; 省份記錄裡的一個 word
        call    sub_5C7FE
        or      al, al
        jnz     loc_1102C           ; 1. 成立 → 進戰鬥
        cmp     byte_7003A, 0
        jnz     loc_1102C           ; 2. 成立 → 進戰鬥
        cmp     byte_7003B, 0
        jnz     loc_1102C           ; 3. 成立 → 進戰鬥
        jmp     loc_11143           ; 都不成立 → 這個省跳過
```

三個條件是 **OR**，任一成立就打。

### 條件 1：司令是不是十大勢力之一（`sub_5C7FE`）

```
sub_5C7FE(arg: word) -> boolean
    if byte_7003A != 0:  return false
    if arg == 0:         return false
    for i = 1 to 10:
        if arg == 表[i]: return true
    return false
```

**在一個 10 元素的 word 表裡線性搜尋**。第一期正好有 10 個勢力
（張作霖、孫傳芳、吳佩孚、蔣中正、劉湘、唐繼堯、袁祖銘、趙恆惕、閰錫山、馮玉祥，
見 `docs/spec/03` §3），而傳進去的 word 來自省份記錄，司令欄位存的正是將領 ID。

- 迴圈從 **1** 數到 10，不是 0——與將領 ID 是 1-based 一致（SPEC-03 §3）。
- `arg == 0` 直接回 false，對應「無主的省」。

**傳入的是司令 ID 已經是 confirmed**——§5 從另一條路（`sub_3964E` 用同一個
基址讀 `+20`、寫 `+0`／`+2`）交叉印證了這一點。

⚠️ 但**十大勢力表本身的內容是執行期填的，靜態看不到**。
「表裡裝的就是那十位領袖」仍是從「10 這個數字 + 傳入的是司令 ID」推的
**強證據**，要完全確認得動態 dump 或找到填表的程式碼。

### 條件 3：`byte_7003B` 是「觀戰」開關 — **confirmed（程式碼）／強證據（語意）**

`byte_7003B` 全 `WAR.EXE` **只有一個寫入點**：`sub_1BF58`，而那是個 toggle：

```asm
cmp     byte_7003B, 0
mov     al, 0
jnz     short loc_1C04B
inc     ax                      ; 0 → 1
loc_1C04B:
mov     byte_7003B, al
... 畫一個框 ...
cmp     byte_7003B, 0
jz      short loc_1C08B
OUTTEXTXY(..., "ON")            ; 開
jmp     short loc_1C09D
loc_1C08B:
OUTTEXTXY(..., "OFF")           ; 關
```

**輸出 ON/OFF 字串的設定開關**。`sub_1BF58` 由 `sub_1C38C` 呼叫，
是設定選單的一項。

配合 `2.15` 詞條 147「**觀戰**」，方向相反的謎就解開了：

| 位置 | 開關打開時 | 讀起來 |
|---|---|---|
| `sub_5C7FE` 開頭 | return false | 「這個省不算我的勢力」|
| 主迴圈 gate | 進戰鬥 | 「但還是要進去看」|

**觀戰模式：不是自己的省也進戰鬥畫面**。兩處行為完全自洽。

⚠️ 語意標**強證據**而非 confirmed——ON/OFF 開關與 toggle 行為是讀到的，
「這個開關叫觀戰」是從詞表與兩處用法推的，沒有直接讀到標籤字模。

### 條件 2：`byte_7003A` — **未知**

只在 `PROGRAM` 初始化時設 0，**全檔沒有其他寫入點**。
所以在正常流程下它恆為 0，這個條件永遠不成立——可能是開發期的 debug 旗標。

`sub_5C7FE` 開頭也檢查它（非 0 直接 return false），與 `7003B` 同樣的用法。

## 3. 進戰鬥前會釋放政略階段的記憶體 — **confirmed**

`loc_1102C` 在呼叫戰鬥主函式 `sub_39B6E` 之前，連續七次 `FreeMem`：

```
0xB08, 0x520, 0xA38, 0x520, 0xA98, 0x298, 0x718 bytes
```

政略與戰鬥的狀態是**分開配置**的，不共用緩衝。remake 不需要重現這個
記憶體管理，但它證實了兩個階段的狀態互不干涉——`internal/game` 可以
把政略與戰鬥切成兩組狀態，不必擔心原版有隱藏的共用欄位。

## 4. 隨機決策的分佈 — **confirmed**

`WAR.EXE` 有 **53 個 `Random` 呼叫**（外加開頭一次 `Randomize`），
散在 24 支函式裡。範圍參數直接暴露了機率結構：

| 範圍 | 次數 | 出現在 |
|---:|---:|---|
| `Random(10)` | 18 | 最主力——十分之一骰。`sub_3964E` 一支就佔 6 次 |
| `Random(5)` | 6 | `sub_36D74`(3)、`sub_1AA28`、`sub_1FC1C`、`sub_35B19` |
| `Random(2)` | 6 | `sub_11C04`(3) 等 |
| `Random(500)` | 4 | `sub_21D1D` |
| `Random(349)` | 4 | `PROGRAM`(3)、`sub_3562B` |
| `Random(3)` | 2 | `sub_1A729`、`sub_1AA28` |
| `Random(6)` | 2 | `sub_24535`、`sub_35E89` |
| `Random(278)` | 1 | `PROGRAM` |
| `Random(700)` | 1 | `sub_19918` |
| `Random(60000)` | 1 | `sub_303CD` |
| 其他（8、9、15、20）| 4 | |

`Random(10)` 佔三分之一——**原版的隨機判斷主要是十分之一骰**，
remake 要對齊機率就從這個粒度開始。

⚠️ `Random(278)` 接近 `MAN115` 的 274 位將領但**不相等**，
不要當成「隨機選一位將領」。

## 5. 勢力覆滅時清空該省資源 — **confirmed（程式碼）／假說（語意）**

`sub_3964E`（戰鬥結束後由 `sub_39B6E+6F4` 呼叫，`docs/re/04`）裡有**三段
完全相同**的程式碼，各自跑一個遍歷全省的迴圈：

```
for 省 = 1 to word_7001E:
        di = 37 * 省
        if [di - 6221h] != word_70026:  continue     ; 讀 記錄[省] 的 +20
        di = 37 * 省 + 9DCBh
        [di + 0] = Random(10)
        [di + 2] = Random(10)
```

### 每個常數都對上 SPEC-03

| 組語 | 意義 | 來源 |
|---|---|---|
| `mul 25h` | ×37 = 省份記錄大小 | `docs/spec/03` §1 |
| `[di - 6221h]` | 基址 `0x9DDF` + 省×37 | |
| `di + 9DCBh` | 基址 `0x9DCB` + 省×37 | |
| 兩個基址相差 **20** | `+20` 正是**司令**欄位 | `docs/spec/03` §2 |
| 寫入 `+0`、`+2` | **黃金**與**糧食** | 同上 |

**兩條獨立的線索交叉印證**：戰鬥 gate（§2）讀的也是 `[di-6221h]`，
所以 `sub_5C7FE` 收到的確實是司令 ID——§2 裡標為「強證據」的那一點
**升級為 confirmed**。

### 語意：某個勢力覆滅，它的省被洗掉 — **假說**

程式行為是確定的：**篩出所有司令等於 `word_70026` 的省，
把黃金與糧食重設為 0–9 的隨機值**。

把資源設成個位數等於清空，所以最合理的解釋是「某個勢力被消滅時，
它名下所有省份的資源歸零」。`word_70026` 就是那個勢力的領袖 ID。

三段相同的程式碼很可能對應三種角色（攻方／守方／第三方），
但**沒有驗證**。`byte_70056`、`byte_6BCD1` 與 `byte_6C952` 是進入這段的前置條件，
語意也未解。

### 對 remake 的意義

這是目前唯一一條**讀到程式碼**的結算規則。它同時說明：
省份資料表在戰鬥結算時**會被就地改寫**，政略與戰鬥不是完全隔離的
（雖然記憶體緩衝是分開配置的，見 §3）。

## 6. 政略流程的兩條路徑 — **confirmed（結構）／未知（語意）**

`PROGRAM+446` → `sub_1ACCC` → `+255` → `sub_15F3C` 是政略階段的處理鏈。

`sub_15F3C` 開頭先清空 8 格暫存（8 = 鄰省表的大小），然後用
**`sub_5B7DC` 的回傳值分流**——那支回傳「第一個可攻打的鄰省」
（`20-military.md` §1b）：

| 分流 | 意義 | 流程 |
|---|---|---|
| 回 0 | **沒有可攻打的鄰省** | `sub_15018` → `sub_15667` → `sub_150FC(1)` → `sub_1527A` → `sub_15925(0)` → *`sub_15A9A`* |
| 回非 0 | **有可攻打的鄰省** | `sub_1541E` → `sub_150FC(2)` → `sub_15925(1)` → *`sub_15A9A`* → *`sub_15CE3`* |

斜體的兩步有額外條件：`byte_6FFCA & 4` 才執行。

### 三個結構特徵

1. **每一步之前都檢查 `[di-7]`**，非 0 就跳過後續——中途取消的旗標。
   使用者按 ESC 或條件不成立時，剩下的步驟全部略過。
2. `sub_150FC` 與 `sub_15925` **同一支函式用不同參數**（1/2、0/1），
   代表兩條路徑共用邏輯、只差模式。
3. `sub_15667`、`sub_150FC`、`sub_1541E` **三支都會遍歷鄰省表**，
   各自屬於不同的步驟。

### 這對 AI 的意義

**電腦的第一個判斷是「有沒有可攻打的鄰省」**，而不是「我想做什麼」。
決策從地理條件出發，這與 §1「決策粒度在省」是一致的設計。

### `sub_15925`：收集候選鄰省，門檻依模式而定 — **confirmed**

兩條路徑都會呼叫它，只差參數（路徑 A 傳 0、路徑 B 傳 1）：

```
門檻 = (arg == 0) ? 5 : 25
清空 8 格候選陣列
if 門檻 > [某個值]:  直接結束        ; 資源／數量不足
for j = 1 to 8:
    n = 記錄[省].鄰省[j]
    if n == 0 or n == 0xFF:        continue
    if !sub_1588C(n):              continue   ; 另一層過濾，內容未解
    if 記錄[n].+32 & 0x40:          continue   ; 位元旗標排除
    候選[++count] = n
```

**5 與 25 是兩個模式的門檻值**。門檻大於某個量就直接結束——
所以這一步是「資源夠不夠做這件事」的檢查，不夠就跳過。
那個被比較的量從呼叫者的 stack frame 取（Pascal 巢狀函式的 static link），
**是什麼還沒追**。

這一步同時揭露了省份記錄 `+32` 是位元旗標欄位（`docs/spec/03` §2b）——
`0x40` 設了的省會被排除在候選之外。

### `sub_1588C`：與攻打規則同一套過濾 — **confirmed**

`sub_15925` 用它當第二層過濾。內容與 `sub_5B7DC`（`20-military.md` §1b）
同一套判準：

```
if 記錄[n].司令 == 0:                    → 否決   ; 無主
if 記錄[n].司令 == [呼叫者的勢力]:        → 否決   ; 同勢力
```

所以候選收集的過濾是**兩層疊加**：先 `sub_1588C` 的勢力判斷，
再 `+32 & 0x40` 的旗標排除。

### `sub_15018`：清點某種將領，再決定分支 — **部分解**

路徑 A 的第一步。前段是一個計數迴圈：

```
count = 0
if byte_6FE88 == 1 and (byte_6FFCA & 4):
    for j = 1 to 24:
        id = 清單[j]                      ; ds:[j*2 - 534Ah]，24 格的 word 陣列
        if id == 0: continue
        if 將領[id].+0 & 1:  count++       ; 33 stride，基址 7A8Dh
```

後段用 `count` 分支：`count == 2` 時，依 `byte_6FFCA & 1` 走 7 或 5。

**24 格的 word 陣列**裝什麼未知（勢力有 10 個、省有 39 個，都對不上 24）。

#### [訂正] 這裡讀的是 `+16`，不是 `+0`

本節原本寫「讀 `將領[id].+0` 的 bit 0」，並據此推論「執行期結構與檔案
結構不同」。**那個偏移我算錯了。**

`sub_15018` 讀的是 `[di + 7A8Dh]`，其中 `di = 33 × id`。
執行期將領表的基址是 **`0x7A7D`**（`sub_54826` 有直接的 `add di, 7A7Dh`），
所以偏移是 `0x7A8D − 0x7A7D` = **16**。

檔案的 `+16` 本來就未解（`docs/spec/02` 只解出 `+0/+1/+2/+4/+17`），
檢查它的 bit 0 沒有任何矛盾。

**執行期與檔案佈局看起來是一致的**——`+4`（所屬省）被 96 支函式存取、
`+17`（兵力）119 次，都是核心欄位該有的熱度。原本的警示不成立，已刪除。

留下的教訓不是「結構會變」，而是**算偏移要拿基址驗**：
基址寫在別的函式裡，光看單一存取點會猜錯。

⚠️ 仍未解：`sub_1527A`／`sub_15A9A`／`sub_15CE3` 的內容，
`byte_6FFCA` 各個位元的意義，24 格陣列裝什麼。

## 6b. 尋路權重與真實成本是分開的 — **confirmed**

這是目前解出來**最具體的一條 AI 行為參數**，也是 remake 要調難度時
一定會用到的東西。

`sub_4FCCC` 建一張 196×196 的全對全成本矩陣（`dword_6A454` 指向的
38,416 bytes）。建之前它會**暫時改寫三種地形的成本**，建完再改回來：

| 地形 | 建矩陣時（尋路權重）| 改回來（真實移動成本）| 倍率 |
|---|---:|---:|---:|
| 河海(3) | **30** | 12 | 2.5× |
| 沙漠(7) | **100** | 4 | **25×** |
| 有鐵路 | **1** | 2 | 0.5× |

矩陣本身的規則：

```
M[i][j] = 0        若 i == j
        = 50h(80)  若相鄰且 j 上面有單位
        = byte_9E2[j]（該格成本）  若相鄰且可通行
        = 0FFh     否則
```

### 這代表什麼

**AI 尋路時看到的地圖與實際走起來的地圖不一樣。** 沙漠實際只要 4 點
機動力，但規劃路徑時算 100——25 倍的差距，等於 AI 幾乎不會規劃穿越沙漠
的路線，即使那是最短路。河海同理（2.5 倍），鐵路則被加倍偏好（0.5 倍）。

這不是 bug，是**故意的行為偏好**：讓電腦部隊看起來「像會沿鐵路調兵、
繞開沙漠」，而不是機械地走最短路。

### 對 remake 的意義

兩組成本要分開實作，不能合成一組。要調電腦對手的行為（`CLAUDE.md` §6.5
說的「未來優化」），**改尋路權重比改真實成本安全**——後者會改變遊戲規則，
前者只改變 AI 的偏好。

真實成本表（`sub_506B0` 的完整分組）見 `30-combat.md` 與 `docs/re/07` §7。

## 6c. 難度／勢力加成：`byte_6FFCA` 的 bit 4–6 — **confirmed**

**這是目前找到最直接的難度參數**，攻擊力公式的最後一段
（`sub_5A0B9`，`docs/re/08` §4e）：

```
if 效忠的勢力是十大勢力之一（sub_5C7FE）:
    d = byte_6FFCA & 0x70
    d == 0x10:                     戰力 ×2
    d == 0x20:                     戰力 ×1.5
    d == 0x40 且 效忠者 == 蔣中正:   戰力 ×1.5
else:
    效忠者 == 蔣中正 且 byte_6FE88 == 1:  戰力 ×1.5
```

三個位元組成一個**三選一的加成設定**，套在「十大勢力」的單位上。

### 為什麼這是難度旋鈕

- `0x10` 讓所有十大勢力的單位戰力**翻倍**——玩家若不是十大勢力之一，
  等於全世界都變強一倍
- `0x20` 是溫和版（×1.5）
- `0x40` 只加給**蔣中正**（將領 ID 1，`docs/spec/03` §3）

而 `else` 那條分支專門給「效忠蔣中正但蔣不算十大勢力」的情況——
公式裡總共有**兩處**為 ID 1 開的特例。這是設計者給主角勢力的偏袒，
不是資料驅動的一般規則。

### 對 remake 的意義

要調整難度，**改 `byte_6FFCA & 0x70` 這一組是最乾淨的入口**——
它不動任何基礎數值，只縮放最終戰力。與 §6b 的尋路權重是同一類旋鈕：
原版把「難度」與「規則」分開了，remake 應該保持這個分離。

⚠️ 誰寫 `byte_6FFCA`、玩家在哪裡選這個設定，**還沒追**。
它的 bit 0 與 bit 2 在政略流程也有人讀（CONTEXT worklist #6d），
那兩個位元與這裡的 bit 4–6 是不是同一組設定，未確認。

## 6d. 電腦選指令的優先序 — **confirmed（結構）**

`CLAUDE.md` §6.5 把「電腦選指令的優先序」列為必記的第一項。
`sub_15F3C` 就是那條鏈。

```
sub_15F3C(狀態):
    暫存[1..7] = 0
    if sub_5B7DC(當前省) != 0:            ; 有敵對的鄰省 → 前線省
        sub_1541E(狀態)
        if 還沒決定: sub_150FC(狀態, 2)
        if 還沒決定: sub_15925(狀態, 1)
        if 還沒決定 且 (byte_6FFCA & 4): sub_15A9A(狀態)
    else:                                 ; 沒有敵對鄰省 → 後方省
        if 還沒決定: sub_15018(狀態)
        if 還沒決定: sub_15667(狀態)
        if 還沒決定: sub_150FC(狀態, 1)
        if 還沒決定: sub_1527A(狀態)
        if 還沒決定: sub_15925(狀態, 0)
        if 還沒決定 且 (byte_6FFCA & 4): sub_15A9A(狀態)
    if 還沒決定 且 (byte_6FFCA & 4): sub_15CE3(狀態)
```

### 三個結構特徵

1. **`ss:[di-7]` 是「已經決定要下什麼指令」的旗標。** 每一步之前都檢查它
   還是不是 0——**一旦某一步做出決定，後面全部跳過**。
   所以這是一條**由上而下的優先序**，不是評分後挑最高分。
2. **前線省與後方省走不同的鏈**，而且**後方省的鏈比較長**
   （6 步 vs 4 步）。合理：後方要做內政與生產，前線只管打。
3. **`byte_6FFCA` 的 bit 2 啟用最後三個決策步驟**（`sub_15A9A` 兩處與
   `sub_15CE3`）。關掉的話電腦少三種行為。

### `sub_5B7DC(省)` = 第一個敵對的鄰省 — **confirmed**

```
我的司令 = 省份[省].+20
for k = 1..7:
    if 我的司令 == 0:                  return 0
    鄰省 = 省份[省].鄰省[k]
    if 鄰省 == 0 或 0FFh:              continue
    if 省份[鄰省].司令 == 0:            continue   ← 無主省不算敵對
    if 省份[鄰省].司令 == 我的司令:      continue   ← 自己人不算
    return 鄰省
```

三個偏移（`+20` 司令、`+22` 鄰省表、`0FFh` 哨兵）都對得上 `SPEC-03`。

**無主省不算敵對**——這與攻打候選的規則（`SPEC-01` §2）一致：
攻打要求「司令不同**且非無主**」。

| `sub_150FC` | **調動**，見 §6e |
| `sub_15925` | 收集候選鄰省 = **攻打**（§6）|

| `sub_1527A`／`sub_15A9A`／`sub_15CE3` | **未讀** |

## 6e. 調動：`sub_150FC` → `sub_14F9A` — **confirmed**

政略指令 1 是「調動行動」（`docs/playtest/02` §5 實機確認）。
決策鏈裡的 `sub_150FC` 就是它，而且**前線省與後方省傳不同的模式**。

### 挑目標省：四道守門

```
for k = 1..7:
    鄰省 = 省份[當前省].鄰省[k]
    if 鄰省 == 0 或 0FFh:              continue   ; 填充／海洋境外
    if 省份[鄰省].司令(+20) == 0:       continue   ; 無主省不調
    if !sub_13F4E(將領, 鄰省):          continue   ; 未讀
    if sub_1401E(將領, 鄰省) 且 模式 == 1:  → 選中它
    if !sub_36BC7(鄰省):                continue   ; 未讀
    if 模式 != 2:                       continue
    if 省份[鄰省].+32 & 40h:            continue   ; **正在打仗的省不調**
    → 選中它
```

`+20`（司令）、`+22`（鄰省表）、`+32` bit 6（正在打仗）三個偏移都對得上
`SPEC-03`。

### 調動類型由目標省的處境決定

```
if 模式 == 2:                        類型 = 4
elif sub_5B7DC(選中的省) != 0:        類型 = 1     ; 目標省有敵對鄰省
else:                                類型 = 0     ; 目標省是安全的後方
sub_14F9A(將領, 類型, 選中的省)
```

配上 §6d 的優先序鏈：

| 省的處境 | 呼叫 | 得到的類型 |
|---|---|---|
| **前線**（有敵對鄰省）| `sub_150FC(2)` | **4** |
| **後方**，目標是前線 | `sub_150FC(1)` | **1** |
| **後方**，目標也是後方 | `sub_150FC(1)` | **0** |

也就是**後方省會把部隊往前線調**（類型 1），前線省之間的調動走類型 4。

### 執行：目標省的司令換人 — **confirmed**

```
sub_14F9A(將領, 類型, 目標省):
    sub_34105(目標省)                       ; 重畫
    sub_1408F(將領, &結果, 類型, 目標省)     ; 實際搬動，未讀
    if 結果 != 0:
        省份[目標省].+20 = 狀態[-2]          ; ← 目標省的司令改成調過去的人
        狀態[-7] = 1                         ; ← 標記「已決定」，優先序鏈到此結束
        sub_34105(當前省)
        if byte_6FE83 != 0: sub_137AB(...)
```

`mov [di-6221h], cx`（`di = 37 × 目標省`）落在記錄 `+20`，正是司令欄位
（`SPEC-03` §2）。**調動的效果就是把某個將領派到鄰省當司令。**

`狀態[-7] = 1` 就是 §6d 那條優先序鏈檢查的旗標——兩邊對上了，
確認整條鏈的控制流沒有讀錯。

⚠️ `sub_1408F`（實際搬動兵力）、`sub_13F4E`、`sub_1401E`、`sub_36BC7`
（三道守門）**都還沒讀**。所以「什麼條件下電腦會調動」只解出骨架。

## 6f. 增援前線：`sub_1527A` — **confirmed**

決策鏈裡的 `sub_1527A` **也呼叫 `sub_14F9A`**，所以它也是調動
——但守門條件與 `sub_150FC` 完全不同：

```
for k = 1..7:
    鄰省 = 省份[當前省].鄰省[k]
    if 鄰省 == 0 或 0FFh:                    continue
    if 省份[鄰省].司令 != 我方的勢力:          continue   ← 只調到自己人的省
    if sub_5B7DC(鄰省) == 0:                 continue   ← 目標省必須是前線
    if !(sub_14761(...) & 1):                continue
    if 省份[鄰省].+32 & 40h:                 continue   ← 正在打仗的不去
    if sub_5A881(鄰省) >= 15:                continue   ← 屯兵上限
    （還有一道與所屬省有關的檢查，frame 跨得深，未完全展開）
    → 選中
```

### 三條與 `sub_150FC` 的差別

| | `sub_150FC`（一般調動）| `sub_1527A`（增援前線）|
|---|---|---|
| 目標省的歸屬 | 任何**有主**的省 | **必須是自己人** |
| 目標省的處境 | 不限 | **必須有敵對鄰省** |
| 屯兵上限 | 無 | **可用將領數 < 15** |

所以 `sub_1527A` 的語意很清楚：**後方的將領往自己人的前線省集中，
但一個前線省最多屯 15 個將領。**

### 15 是真的會生效的門檻

`sub_5A881(省)` 是「該省效忠其司令且可用的將領數」（`docs/re/07` §9）。
先前在戰鬥增援 `sub_534FF` 看到的同一個函式配的是 `>= 100`
——那條**實質恆真**（全遊戲才 274 位將領）。

這裡是 **15**，而河南在 `SAVE(1)` 就有 25 位將領——**這條會真的擋住**。

**這是目前解出來最具體的一條 AI 行為參數**：電腦不會把所有部隊
堆到同一個前線省。要調整電腦的集結傾向，改這個數字最直接。

## 6g. `sub_14761`：這個省有沒有滿員／缺員的將領 — **confirmed**

決策鏈上四支函式的守門條件都出自這裡。

```
旗標 = 0
for id = 1 .. word_6BC4A:                     ; 全部將領
    if !(單位[id].+16 & 1):        continue    ; 不可用
    if 單位[id].+4 != 省:          continue    ; 不在這個省
    if 省份[省].司令 == id:        continue    ; 司令本人不算
    滿員 = Round(sub_349C1(id) × 20000)
    if 單位[id].兵力 == 滿員:       旗標 |= 1   ; ← bit 0
    elif 單位[id].兵力 < Round(sub_349C1(id) × 10000):
                                   旗標 |= 2   ; ← bit 1
return 旗標
```

| 位元 | 意思 |
|---:|---|
| 0 | 這個省**有兵力剛好滿員**的將領 |
| 1 | 這個省**有兵力不到半員**的將領 |

### 誰用哪一個位元

| 決策 | 檢查 | 讀起來 |
|---|---|---|
| `sub_1527A` 增援前線 | **bit 0** | 有滿員的部隊才調出去 |
| `sub_1541E`／`sub_15667` | **bit 1** | 有缺員的部隊才做某件事 |

**bit 1 那兩支很可能是徵兵／整編**——詞表有「徵兵」「整編」
「重新整編」「整編兵力」（`2.15`），而「有部隊缺員」正是那兩個指令的
前提。⚠️ 兩支的內容（各 290／276 行）**還沒讀**，這是方向不是結論。

### 滿員 = 20000 ÷ 兵種權重 — 原版明確算的

`sub_349C1(id)` 回傳一個係數，乘 20000 就是該將領的滿員兵力：

| 兵種 | 人力權重（`sub_5190E`）| 20000 ÷ 權重 | 資料實測 |
|---:|---:|---:|---:|
| 1 步兵 | 1 | 20,000 | 20,000 ✓ |
| 4 砲兵 | 10 | 2,000 | 2,000 ✓ |
| 5 裝甲兵 | 100 | 200 | 200 ✓ |
| 6 騎兵 | 2 | 10,000 | 10,000 ✓ |

`docs/spec/02` §6 原本把「權重 × 滿員 = 20000」記成**觀察**
——現在知道那是**原版程式明確算出來的**，`sub_349C1` 就是 `1 ÷ 權重`。

### 第二個藏在 Real 裡的滿員數

```
0x8F, 0x0000, 0x1C40  →  20000    （攻擊力公式的分母，docs/re/08 §4a）
0x8E, 0x0000, 0x1C40  →  10000    ← 這裡
```

兩個常數只差 exponent 一階（143 vs 142），尾數完全相同。
`CLAUDE.md` §1.5 那四個滿員數裡，**20000 與 10000 都是字面常數**
（只是編碼成 48-bit Real），2000 與 200 則是除出來的。

### 對 remake 的意義

**電腦的行為是一條寫死的優先序，不是效用函式。** 要改難度或行為，
可以在鏈上插隊或換順序，而不必重寫評分——這與 §6b（尋路權重）、
§6c（戰力加成）一樣，原版把「行為」與「規則」分開了。

## 6h. `sub_1541E`：前線省把缺員的部隊撤到後方 — **confirmed（結構）**

決策鏈裡**前線省的第一步**（§6d 路徑 A）。它也呼叫 `sub_14F9A`，
所以也是調動——但方向與 §6e、§6f 都相反。

```
if !(sub_14761(當前省) & 2):        return    ; 省內沒有缺員的部隊 → 不做
if 狀態[-236h] / 狀態[-22Eh] < 10000: return  ; 一道比值門檻，見下

候選 = []
for k = 1..7:
    鄰省 = 鄰省表[k]
    跳過 0／0FFh
    if 省份[鄰省].司令 != 我方勢力:   continue   ; 只找自己人
    if sub_5B7DC(鄰省) != 0:         continue   ; **目標省必須是後方**
    if 省份[鄰省].+32 & 40h:         continue   ; 正在打仗的不去
    if !sub_13F4E(將領, 鄰省):       continue
    候選 += 鄰省

依 sub_5B983(省) **升序**排序候選
sub_14F9A(將領, 4, 候選[0])          ; 挑戰力總和**最小**的那個
```

### 三種調動的方向完全不同

| 決策 | 在哪條鏈 | 目標省 | 前提 |
|---|---|---|---|
| `sub_1541E` §6h | 前線 | 自己人的**後方**省 | 有**缺員**的部隊（bit 1）|
| `sub_150FC` §6e | 兩條都有 | 任何**有主**的省 | — |
| `sub_1527A` §6f | 後方 | 自己人的**前線**省 | 有**滿員**的部隊（bit 0），且該省將領 < 15 |

讀起來是一組完整的輪調：**滿員的往前線送，缺員的撤回後方**。

### 排序鍵 `sub_5B983(省)` = 該省可用將領的戰力總和 — **confirmed**

```
總和 = 0
for id = 1 .. 將領總數:
    if 單位[id].+4 != 省:      continue    ; 不在這個省
    if !(單位[id].+16 & 1):    continue    ; 不可用
    總和 += sub_5A0B9(id)                   ; ← 攻擊力公式
return 總和                                 ; 32-bit
```

**AI 用的評估函式就是攻擊力公式 `sub_5A0B9`**（`docs/re/08` §4）。
這對 remake 很重要：規則層的 `game.Strength()` 不只算戰鬥，
**同時是電腦評估局勢的工具**——兩邊必須用同一份實作，
否則 AI 的判斷會與實際戰果脫節。

排序是**升序**（`i > j` 才交換），所以挑的是**戰力總和最小**的後方省。
讀起來像「把缺員的部隊補到最弱的後方」，但那是解讀不是證據。

### ⚠️ 那道 10000 的門檻沒解

`狀態[-236h]`（32-bit）÷ `狀態[-22Eh]` 必須 ≥ `2710h` = 10,000。

`-22Eh` 在 `sub_15667` 裡被檢查 `>= 3`，所以是個小數字。
若它是「該省的將領數」而 `-236h` 是「兵力總和」，這道門檻就是
**平均兵力 ≥ 10,000**（半個滿員步兵師）——**但這是假說**，
那兩個 local 的來源還沒追。

## 6i. 決策鏈的全貌：六個步驟都是調動，差在挑目標的條件 — **confirmed**

把 §6d 那條鏈的每一步都追過之後，浮現一個整體認識：

> **政略階段電腦做的事，主要就是「調動」與「攻打」兩種。**
> 決策鏈的六個步驟裡有五個呼叫 `sub_14F9A`（調動），
> 只有 `sub_15925` 是攻打。差別全在**挑哪個省當目標**。

| 步驟 | 鏈 | 前提 | 目標省的條件 | 排序／挑選 |
|---|---|---|---|---|
| `sub_1541E` §6h | 前線 | 有缺員部隊 + 一道 10000 門檻 | 自己人的**後方**省，未交戰 | 戰力總和**最小** |
| `sub_150FC` §6e | 兩條 | — | 任何**有主**的省；模式 2 跳過交戰中的 | 掃到就選 |
| `sub_15667` §6j | 後方 | 有缺員部隊 + **將領數 ≥ 3** | **後方**省，未交戰，**將領數比自己少** | 戰力總和**最小** |
| `sub_1527A` §6f | 後方 | 有滿員部隊 | 自己人的**前線**省，未交戰，**將領數 < 15** | 掃到就選 |
| `sub_15A9A` §6k | 兩條 | **將領數 ≥ 4** | 資源達標的省 | 掃到就選 |
| `sub_15CE3` | 最後 | `byte_6FFCA & 4` | **未讀**（也呼叫 `sub_14F9A` 與 `sub_5B983`）| |
| `sub_15925` | 兩條 | — | 可攻打的鄰省 | **攻打** |

### 一以貫之的傾向：分散，不集中

三處獨立的上限都在防止兵力堆在一個省：

- `sub_1527A`：前線省的將領數 **≥ 15 就不再增援**
- `sub_15667`：只往**將領數比自己少**的省分
- `sub_1541E`／`sub_15667`：排序挑**戰力總和最小**的省

**這是原版 AI 的核心行為特徵。** 要讓電腦更會集中兵力（更難打），
改這三處比改任何數值都直接。

## 6j. `sub_15667`：後方省往人少的地方分兵 — **confirmed（結構）**

| | `sub_1541E`（前線）| `sub_15667`（後方）|
|---|---|---|
| 第二道門 | `x / y ≥ 10000` | **當前省將領數 ≥ 3** |

一次算目標省，然後比大小。

## 6k. `sub_15A9A`：往補給充足的省調動 — **confirmed（門檻）**

需要 `byte_6FFCA & 4` 才會執行（§6d）。它的守門是**資源門檻**：

```asm
cmp word ptr ss:[di-22Eh], 4        ; 當前省將領數 ≥ 4
cmp word ptr [di-6235h], 1388h      ; 目標省 +0  黃金 ≥ 5,000
cmp word ptr [di-6233h], 7530h      ; 目標省 +2  糧食 ≥ 30,000
cmp word ptr [di-6231h], 7530h      ; 目標省 +4  彈藥 ≥ 30,000
cmp word ptr [di-622Dh], 7530h      ; 目標省 +8  燃料 ≥ 30,000
```

四個偏移（基址 `-6221h` = 記錄 `+20`）算回去正好是 `SPEC-03` §2 的
黃金／糧食／彈藥／燃料，**順序完全對上**。

| 資源 | 門檻 |
|---|---:|
| 黃金 | 5,000 |
| 糧食 | 30,000 |
| 彈藥 | 30,000 |
| 燃料 | 30,000 |

**黃金的門檻只有其他三項的六分之一。** 而資源上限是 60,000
（`docs/mechanics/40-economy.md`），所以糧食／彈藥／燃料的門檻是**半滿**。

語意：**把部隊調到補給充足的省。** 這也是一條可調的難度旋鈕
——門檻放寬，電腦就更常做後勤調度。

⚠️ 排序方式與 `sub_15CE3` 的內容還沒讀。

## 6l. 規則層實作與已知差異

決策鏈實作在 `internal/game/ai.go`（`AIWorld.Decide`）。
拿 `SAVE(1)` 的真實局面跑一遍：

```
前線省 17 個、後方省 12 個
決策分佈：一般調動 18、撤回後方 6、分兵 5、攻打 0
```

### ⚠️ 攻打 0 次是實作的限制，不是原版行為

原版每一步除了已解出的挑選條件，還有幾道守門
（`sub_13F4E`／`sub_1401E`／`sub_36BC7`）**尚未讀出**。

沒有它們，`sub_150FC`（一般調動）的條件只剩「鄰省有主」——幾乎總是成立，
於是**它吃掉所有決策，排在後面的攻打永遠輪不到**。

這是「優先序鏈」這種結構的固有風險：**漏掉一道守門，後面所有步驟一起消失**，
而且不會報錯，只會表現成「電腦不打仗」。與評分式的 AI 不同——那種漏一個
權重只是分數偏掉。

所以下一步的優先序很清楚：**先讀那三道守門**，其餘細節都在其次。
