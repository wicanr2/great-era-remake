# 遊戲機制索引

依 `CLAUDE.md` §6.5：每解出一條機制就按屬性歸檔到這裡。
規格檔（`docs/spec/`）寫「資料長什麼樣」、反組譯筆記（`docs/re/`）寫「程式碼在哪」，
**這批文件寫「遊戲是怎麼運作的」**。

remake 完成之後的優化——尤其是改進電腦 AI——全靠這批文件。

---

## 推論等級

每一條機制都要標，不准為了看起來完整而編：

| 標籤 | 意思 |
|---|---|
| **confirmed** | 反組譯讀到程式碼，或實機多次重現 |
| **強證據** | 資料全量對得上，但沒讀到程式碼 |
| **假說** | 合理但只有間接證據 |
| **未知** | 還沒解，附「下一步從哪挖」|

社群資料（巴哈攻略、維基）**一律先標假說**，直到在執行檔或實機驗到為止
（`CLAUDE.md` §4 的 oracle 優先序）。

## 定機制的第一動作：查畫面地圖

`docs/re/27-screen-map.md` 把 `WAR.EXE` 裡 93 個函式的畫面文字列成一張表
（原理見 `docs/re/24`，工具 `tools/glyph_calls.py`）。

**要弄清楚某個機制時，先查那張表再讀組語。** 它直接告訴你
「哪一支函式在做這件事、畫面上寫什麼字、有哪些失敗分支」——
`docs/re/26` 就是靠它一次定出指令 8 的整個畫面，省掉讀 1,147 行。

⚠️ 那是**導航圖不是規格**。要寫規則層仍然要讀該函式的組語，
表只負責告訴你該讀哪一支。

## 給後續工作的提醒

反組譯時碰到下列任何一種，**當場記進 `70-ai.md`**，不要想著之後回頭補：

- 電腦勢力選指令的優先序
- 出兵目標的挑選規則
- 兵力配置、派將的挑選
- 撤退／求和的門檻
- 任何帶 `Random` 的判斷（亂數在哪介入、範圍多大）
- 難度參數

漏掉的代價是整段反組譯要重做一次。
