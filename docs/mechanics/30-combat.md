# 機制：戰鬥

推論等級的定義見 `00-index.md`。

> **這一份幾乎全是未知。** 戰鬥系統是 M3 最大的一塊，也是目前最沒進展的一塊。
> 不要因為社群資料寫得很具體就當成事實——`CLAUDE.md` §4 的 oracle 優先序裡
> 社群資料是最低位階，而且這款遊戲三十年來有大量修改版流傳。

## 1. 已知的硬事實

### 戰場是每省一張 14×14 格 — **confirmed**

三個檔案各管一件事，見 `docs/spec/01`（地名）與 `docs/spec/04`（地物）：

| 檔案 | 每格存什麼 |
|---|---|
| `WARPOS.DAT` | 屬於哪個鄰省（0 = 本省腹地）|
| `TERNAME.DAT` | 地名索引，指向 `TN15.<省>` |
| `NWMAP.DAT` | 地物編號，決定畫哪張圖塊 |

### 戰鬥狀態記錄 469 bytes — **confirmed（結構）／未知（語意）**

`MEM_WAR.DAT` 與 `SAVE(N).DT2` 同結構，見 `docs/re/05`。
10/10、20/20、200/200 三組成對，**很可能是攻守雙方各一份**。

⚠️ 不能拿 `MEM_WAR.DAT` 當戰前基準去 diff 部隊欄位——**8 個省有未初始化的殘料**，
緬甸那筆裡甚至是 8086 機器碼。

### 戰鬥觸發在主迴圈 — **confirmed**

見 `70-ai.md` §2。三個 OR 條件，任一成立就打。

### 戰鬥模組的位置 — **confirmed**

`sub_39B6E`，主迴圈直接呼叫。生命週期是
載入地圖 → 載入戰鬥狀態 → （主迴圈）→ 寫回戰鬥狀態，見 `docs/re/04`。

`+18F` 到 `+6F4` 之間是戰鬥主迴圈，裡面有 `KEYPRESSED`（輸入）與
`SETACTIVEPAGE`（雙緩衝）。

## 2. 詞表證實的戰鬥組成 — **強證據**

原版 UI 詞表（`01-vocabulary.md` §2）裡有這些詞，證明機制存在：

- **機動力**（`3.15` 51）——**已解**：執行期單位記錄的 `+6`／`+7`，
  移動一格扣掉該步成本（`docs/re/07` §7）。成本公式仍未解
- **肉搏戰**（`3.15` 50）——獨立的一個階段或判定
- **攻擊力**（`3.15` 42）、**單位數**（48）、**士兵數**（49）
- **協同攻擊**與**正規攻擊**（`4.15` 40、41）——**兩種攻擊方式，
  社群資料完全沒提到**
- 移動、撤退、駐軍、炮擊、炮轟、行軍、崩潰、衝鋒、增援、損失、陣亡
- **穿越**、**阻隔**——**已解**：長城段（地物 12–21）阻擋通行，
  單位記錄 `+21 == 1` 的兵種可以穿越（`docs/re/07` §7）
- **強渡**——河海的通行規則，未解
- **地方可退**（`4.15` 44）——撤退需要有可退的格子
- **所在地形**（`4.15` 50）——戰鬥中會顯示格子的地形

「單位數」與「士兵數」是兩個不同的量，呼應戰鬥狀態記錄裡
10 個槽 vs 200 B 單位區的雙層結構（`docs/re/05`）。

**這些都只證明存在，不告訴我們公式。**

## 3. 戰鬥選單有七項，不是六個方向 — **confirmed（程式碼）**

`WAR.EXE` 裡**只有一支函式**比較 `'6'`：`sub_38DFE`（`0x38DFE`，
就在戰鬥主函式 `sub_39B6E` 隔壁，同一個編譯單元）。它處理的是
**`'1'` 到 `'7'` 共七個鍵**，每個分支都做同一件事：

```asm
cmp     al, 31h              ; '1'
jnz     ...
mov     al, byte_6FFCA
... 座標常數 ...
call    sub_5A4BC            ; 畫新位置
call    PUTIMAGE             ; 擦舊位置
```

座標：x 固定 243–258（寬 15），y 在 98／114／163／181／229／244／264
之間跳，每格高 10。**這是選單項目的高亮游標**，不是戰場上的移動。

### 這對「數字鍵 1–6 對應六個方向」的社群說法意味著什麼

`CLAUDE.md` §1.5 記的是社群資料（oracle 最低位階）。

程式碼裡唯一的數字鍵分派是**七項**的選單，而且做的是選單繪圖。
**沒有找到「1–6 = 六個方向」的證據。**

這不等於六角格不存在——`3.15` 的詞表確實有「機動力」，
`NEWICON.TPC` 的飛機有六個朝向（`docs/formats/05` §3）。
但**移動的按鍵不是這一支處理的**，六方向的說法在程式碼裡還沒有對應。

七項是哪七個指令未知。`2.15` 的戰鬥詞裡有移動、撤退、駐軍、炮擊、
行軍、衝鋒等候選。

## 3b. 戰鬥結算是九個步驟 — **confirmed**

戰鬥主迴圈 `sub_39B6E` 逐一處理戰場單位：

```
loc_39E50:  var_2A++                        ; 單位索引
    id = word[0x750 + var_2A*2]             ; 戰場單位清單（將領 ID）
    if id == 0:                    → 下一輪
    if 單位[id].+5 != 0xFF:         → 處理    ; 0xFF = 空槽
    ...
    sub_54E3B(a, b)                          ; 參數順序依 byte_64901
```

`byte_64901` 取 **1 或 2** 決定參數順序——對應詞表的「攻方」(`2.15` 166)
與「守方」(167)，也就是誰先動。

`sub_54E3B` 本身是九個連續呼叫，全部落在 `0x54000` 段，是一場戰鬥的
完整結算流程：

```
sub_540B2  sub_54391  sub_546D1  sub_543C2  sub_54CFD
sub_54826  sub_5446D  sub_545B0  sub_54DAC
```

九步都**沒有 `Random` 呼叫**——戰鬥結算本身不擲骰，隨機性（如果有）
在別處介入。`sub_540B2` 的 56 個加減全是座標運算，是繪圖那一步。

## 3c. 第一條解出來的公式：每回合衰減 20% — **confirmed（程式碼）／未知（欄位語意）**

`sub_54826` 裡有一段完整的算式：

```
for j = 1 to 10:                          ; 每方 10 個單位
    id = 單位清單[j]
    if id == 0: continue
    ptr = 0x7A7D + 33*id                  ; 執行期單位記錄，33 bytes
    if ptr[+30] <= 40: continue           ; 40 以下不衰減
    ptr[+30] -= Round(Real(ptr[+30]) / 5.0)
```

### 那個常數是 5.0

浮點常數存在 `CX:SI:DI = 0x0083, 0x0000, 0x2000`。
Turbo Pascal 的 48-bit `Real`：第一個 byte 是 biased exponent（bias 129），
其餘五個 byte 是尾數（最高位元是符號）。

```
exponent 0x83 = 131  →  2^(131-129) = 4
尾數最高 byte 0x20   →  1.01₂ = 1.25
4 × 1.25 = 5.0
```

除以 5 再四捨五入相減，等於**每回合扣掉當前值的 20%**，
但只在該值大於 40 時才扣。

⚠️ **`+30` 是什麼欄位還不知道。** 候選是「體力」或「士氣」
（`2.15` 詞條 80、81）——衰減型的量都符合，但沒有證據指定哪一個。
「10 個單位」呼應 `docs/re/05` 那份 469 B 戰鬥狀態記錄裡每方 10 個槽。

## 3d. 回合初始化：`sub_5446D` 與 `sub_545B0` — **confirmed**

九步結算裡的第六、七步，都遍歷 `word[0x6742 + i*2]` 的單位清單
（與主迴圈用的 `0x750` 是**兩份不同的清單**，很可能是攻守各一）：

```
sub_5446D 對每個單位：          sub_545B0 對每個單位：
    +16 = 1                        +14 = 參數
    +5  = 0xFF                     +8  = 0
    +7  = +6                       sub_5A031(id)
    +13 = 0                        +16 = 1
    +8  = 0                        if byte_64901 == 2: ...
```

### 兩個可讀的模式

1. **`+7 = +6`** 是典型的「當前值 = 最大值」重置。**已確認是機動力**：
   `sub_4A1C0` 移動一格時做 `+7 -= 成本`，呼叫端先檢查 `+7 >= 成本`
   才准走（`docs/re/07` §7）。對上 `3.15` 詞條 51「機動力」。
2. **`+16 = 1`** 與 `sub_15018` 檢查的 `+16 & 1` 對上：
   那個 bit 是「這個單位在場／可行動」。

### 執行期單位記錄的已知欄位

基址 `0x7A7D`，每筆 33 bytes（與 `MAN(N).DAT` 同大小，**佈局不同**）：

| 偏移 | 用法 | 出處 |
|---:|---|---|
| +5 | **戰場格編號 0..195**，`0xFF` = 不在場上 | `sub_50FF5`、`sub_41513`（`docs/re/07` §2）|
| +6 | **機動力上限** | `sub_5446D`（`+7 = +6` 的來源）|
| +7 | **剩餘機動力**，每回合回到 `+6`；移動一格扣掉該步成本 | `sub_5446D`、`sub_4A1C0`（`docs/re/07` §7）|
| +8 | 每回合歸零 | `sub_5446D`、`sub_545B0` |
| +13 | 每回合歸零 | `sub_5446D` |
| +14 | 從呼叫參數設定 | `sub_545B0` |
| +9 | **所屬省編號**（部署時決定從哪一側進場）| `sub_4F0E2` 寫進 `byte_6AB65`，`sub_41513` 比對 |
| +21 | **兵種編號**（強證據；值域含 1/4/5/6）。`== 1` 可穿越長城 | `sub_4A583`、`sub_1629E` |
| +16 | bit 0 = 在場／可行動；部署時 `\|= 4` | `sub_15018` 讀、`sub_5446D`／`sub_545B0`／`sub_41513` 寫 |
| +30 | > 40 時每回合減 20% | `sub_54826` |

## 3e. 兩張單位清單 = 攻守雙方 — **confirmed**

執行期有兩張相鄰的單位清單：

```
0x750  第一方的 10 個單位
0x764  第二方的 10 個單位     ; 0x764 - 0x750 = 0x14 = 20 bytes = 10 個 word
```

`sub_543C2` 對**兩張都**做回合初始化（`+16=1`、`+7=+6`、`+13=0`），
`sub_5446D`／`sub_545B0` 則走第三張 `0x6742`。

**每方 10 個單位現在有三處獨立佐證**：469 B 記錄的槽數、
衰減迴圈跑 1..10、以及這兩張表的距離。

## 3f. 佔領：`sub_54DAC` — **confirmed**

九步結算的最後一步：

```
sub_5ADA6(當前省)
byte[當前省 - 0x435B] = 0
記錄[當前省].+32 &= 0xBF              ; 清除 bit 6
if [arg_0+8] == word_64942:
    記錄[當前省].+20 = word_64942      ; **司令改成勝方**
sub_5A541(當前省, [arg_0+8])
```

`+20` 是省份記錄的司令欄位（`docs/spec/03` §2），把它改掉就是**易主**。
`2.15` 的詞條 186「攻克」、219「佔領」對應的就是這一步。

### 這順帶解掉了 `+32` 的 bit 6

先前只知道 `sub_15925` 收集候選鄰省時會跳過設了它的省，語意未解。
現在加上「戰後 `&= 0xBF` 清除」，語意就清楚了：

> **bit 6 = 這個省正在打仗。**

不能挑正在打的省當目標，打完就清掉。這也解釋了為什麼兩份存檔裡
都沒有出現過——存檔時不在戰鬥中（`docs/spec/03` §2b 已更正）。

## 3g. 單位陣亡：`sub_53DA9` — **confirmed**

`sub_54826` 的核心迴圈：

```
for j = 1 to 10:
    id = 單位清單[j]
    if id == 0:                  continue
    if !(單位[id].+16 & 1):       continue   ; 不在場
    sub_53DA9(1, &結果, &var_DF, id)
    if 結果 != 0:  單位清單[j] = 0            ; **清空槽位 = 陣亡**
```

接著對第二張清單 `0x6742` 做同樣的事（`byte_64901 == 2` 時）。
把槽位設 0 就是把單位從戰場移除——對應詞表的「陣亡」(`2.15` 152/177)。

### `sub_53DA9` 的結果套用

```
if 單位[id].+8 != 0 and id == word_64902:
    var_11 = 1
sub_52129(0, id)
ptr = 0x7A7D + 33*id
ptr[+16] = 1                                  ; 標記在場
ptr[+29] = var_12
ptr[+14] = var_14
ptr[+30] -= Round(Real(ptr[+30]) / 10.0)      ; **扣 10%**
if var_11 != 0:
    byte_6A40A = 1
    byte_64901 = 2                            ; 換方
```

## 3h. 同一個欄位有兩條衰減規則 — **confirmed**

`+30` 在戰鬥的不同階段用不同的除數：

| 出處 | 除數 | 門檻 | 效果 |
|---|---:|---|---|
| `sub_54826`（每回合結算）| 5.0 | > 40 才扣 | 扣 20% |
| `sub_53DA9`（戰鬥判定後）| 10.0 | **無門檻** | 扣 10% |

兩個常數都是 Turbo Pascal 的 48-bit Real：

```
0x0083/0x0000/0x2000  →  2^(131-129) × 1.25 = 5.0
0x0084/0x0000/0x2000  →  2^(132-129) × 1.25 = 10.0
```

### ⚠️ 10% 那條的捨入規則未確認

`v / 10` 的小數**會碰到 .5**（v = 5, 15, 25, …），而 `v / 5` 碰不到——
所以 20% 那條怎麼捨入都一樣，10% 這條不行。

Turbo Pascal 的文件說 `Round` 在正好一半時取絕對值較大的那個
（half-away-from-zero），實作照這個寫。但 Delphi 之後改成 banker's
rounding，**而我們沒有實機驗證過這一版 RTL 的行為**。

差異只在 `v ≡ 5 (mod 10)` 的 26 個值上，各差 1。要確認就實機打一場，
記錄該欄位的變化序列。

## 3i. 誰是攻方：`sub_54391` 與 `sub_54CFD` — **confirmed**

`sub_54391` 只有 24 行，但決定了整場戰鬥的視角：

```
if [arg_0+8] == word_64942:  byte_64901 = 1
else:                        byte_64901 = 2
byte_6A40A = 1
byte_6A8F2 = 1
```

`sub_54CFD` 用同一個判斷選資料：

```
if [arg_0+8] == word_64942:  用 word_64902   ; .DT2 的 +28
else:                        用 word_64916   ; .DT2 的 +48
```

而 `word_64902` / `word_64916` 是 `MEM_WAR.DAT`／`.DT2` 記錄的
`+28` 與 `+48`（`docs/re/05` §2），也就是**攻守雙方各 10 個的參戰單位清單**。

`sub_54DAC`（佔領）也用同一個判斷：`[arg_0+8] == word_64942` 時
才把省份的司令改成 `word_64942`——**攻方贏了才易主**。

所以 `word_64942` 是攻方的識別，`byte_64901` 是「當前處理的是攻方(1)
還是守方(2)」。

### 已實作的部分

`internal/game/combat.go` 與 `province.go` 放了已解出的規則：

| 函式 | 對應 |
|---|---|
| `Decay()` | `sub_54826` 的每回合衰減（20%，門檻 40），整數版與浮點算式 0–255 全域等價 |
| `CombatDecay()` | `sub_53DA9` 的戰鬥衰減（10%，無門檻）|
| `CombatUnit.BeginTurn()` | `sub_543C2`／`sub_5446D` 的 `+7 = +6` 重置 |
| `Battle` / `Side` | 兩張 10 格單位清單 |
| `Province.Capture()` | `sub_54DAC` 的佔領結算（清 bit 6、改司令）|
| `BattleState.Attackers()` / `Defenders()` | `.DT2` 的 `+28`／`+48` 參戰單位清單 |

**沒解出來的欄位語意不猜**，結構裡只放已知用途的欄位。

⚠️ **不要把這些偏移套到 `MAN(N).DAT`**。檔案的 `+0/+1/+2` 是能力值、
`+4` 是所屬省、`+17` 是兵力（`docs/spec/02`），與這裡對不上——
執行期結構與檔案結構是兩回事（`70-ai.md` §6 的方法論警示）。

## 4. 六角格 — **confirmed（排列）／未知（鄰接規則）**

社群資料說「戰鬥用六角格」。`sub_50FF5` 證實了排列方式（`docs/re/07` §3）：

```
col = cell mod 14        x = col × 32
row = cell div 14        y = row × 24 + (col 為奇數 ? 12 : 0)
```

**奇數欄整體下移半格**，這就是 column-staggered 六角格。
原本記的矛盾點（「戰場資料是 14×14 方格，不是六角」）**解消了**：
資料確實是 14×14，六角是繪製與鄰接的解讀方式，兩者不衝突。

旁證也對上了：`NEWICON.TPC` 的飛機圖示有六個朝向（`docs/formats/05` §3）。

### 六角鄰接 — **confirmed**

位移表由 `sub_4E65C` 填、邊界規則在 `sub_510E0`（`docs/re/07` §6）：

| dir | 方向 | 偶數欄 | 奇數欄 |
|---:|---|---:|---:|
| 1 | 左下 | −1 | +13 |
| 2 | 下 | +14 | +14 |
| 3 | 右下 | +1 | +15 |
| 4 | 左上 | −15 | −1 |
| 5 | 上 | −14 | −14 |
| 6 | 右上 | −13 | +1 |

左右緣要裁：偶數欄在 `col == 0` 時沒有左下與左上，奇數欄在 `col == 13` 時
沒有右下與右上。上下邊界不另外檢查，靠 `0..195` 的範圍測試擋掉。

`sub_55CEC(unit, cell, n)` 用這張表數**該格周圍的敵方單位數**，
`n = 1` 只數六格、`n = 2` 連距離 2 的 12 格一起數。距離 2 的位移是
把距離 1 的位移兩兩相加來的，不是另一份表。

### 部署：從自己那一側進場 — **confirmed**

`sub_41513` 把部隊放上戰場的規則：

1. 從 cell **195 往下掃到 0**
2. 該格的 `WARPOS` 值 == 攻方來源省編號（也就是攻方那一側的進場區）
3. `sub_55CEC(unit, cell, 1) == 0`——**落點周圍六格不能已經站著敵人**
4. 該格沒有人站
5. 寫 `單位[+5] = 格`、`佔用表[格] = 單位`，兩邊互指

掃完一輪沒放成功會再跑一輪，**跳過第 3 關**——找不到理想格就硬塞，
這是原版行為。

每個進場區恰好 10 格，與 10 個部隊槽對應。
